# 02 技術監査

サイトのページが「クロールされる → インデックスされる → 意図した URL で検索結果に出る」状態にあるかを、Search Console と `scripts/audit.py` の出力で確かめ、直す順番を決めるためのファイル。

## 1. 目的

- CV につながるページ（`seo/site-brief.md` の主要ページ）が、インデックスを妨げる設定（noindex、robots.txt、canonical、リダイレクト、エラー）を抱えていないか確認する。
- 見つけた課題を影響度 ÷ 工数で並べ（鉄則3）、担当者がそのまま着手できる粒度（対象 URL、原因、直し方、直ったことの確認方法）で出す。
- 対象外: 本文の質は [06-writing-editing.md](06-writing-editing.md)、title・meta description の文面と構造化データの書き方は [07-on-page.md](07-on-page.md)、内部リンクは [08-internal-linking.md](08-internal-linking.md)。このファイルでは「どのページで何が欠けているか」までを出す。

## 2. 必要な入力データ

|---|---|---|---|

## 3. 手順

1. 範囲をそろえる。公開前・公開直後のサイトは、先に下の「公開前・公開直後の点検」を行う。
   - 母集団はサイトマップに載っている URL とする。載っていない URL（パラメータ付き、ファセット）は、ページ インデックス登録レポートのサイトマップ フィルタ「未送信ページのみ」で見る。
   - Search Console のプロパティが URL プレフィックスの場合、http / https、www の有無で別プロパティになる。ドメイン プロパティがあればそちらを使う。
   - ページ数が 500 未満のサイトは、ヘルプでもこのレポートは必須ではないとされている。主要ページを「URL 検査」で1件ずつ確認するほうが早い。数万 URL 以上のサイトや、EC のファセットで URL が増えるサイトは、下の「大規模サイトの監査」も行う。
2. audit.py を実行する。できないこと（JavaScript、表示速度、サイトマップにないページ）は下の「audit.py の限界」で補う。
   - 例: `python3 <スキルのディレクトリ>/scripts/audit.py https://example.jp/sitemap.xml -o seo/audit.csv --limit 500 2> seo/audit_log.txt`（作業フォルダで実行し、出力は作業フォルダの `seo/` に書く。スキルのフォルダには書かない。使い方は `--help`）。
   - 初回は `--limit 500` 程度（1 以上）で傾向をつかみ、必要なら全件を取る。`--limit` はサイトマップの先頭から数え、取得しなかった URL（`BLOCKED:`・`SKIPPED:`）も1件に数えるので、サイトマップの並び（カテゴリ順・更新日順など）によって一部のページの型に偏る。傾向を見るなら、サイトマップ インデックスの子サイトマップを1本ずつ指定し、それぞれ `--limit` で実行する（`-o` は上書きされるので、子サイトマップごとに別のファイルにする）。`--delay` はデフォルト 1.0 秒（0〜3600 秒）で、500 件なら待ち時間だけで 500 秒以上かかる。共用サーバーや他社サイトでは短くしない。`--timeout` はデフォルト 15 秒（0 より大きく 3600 秒以下）。範囲外の値や、`-o` にフォルダ・入力のサイトマップと同じファイルを指定した場合、引数のサイトマップの URL にユーザー名・パスワードが含まれる場合は、理由を表示して終了コード 2 で止まる。
   - 429 / 503 が返ると、Retry-After（秒数か HTTP 日付）があればそれに従って待ち（上限 120 秒）、なければ続いた回数に応じて間隔を `--delay` の2倍ずつ延ばす（上限 60 秒）。429 / 503 を返した URL は取り直さない。5回続くと、サーバーが制限していると判断してクロールを中断し、終了コード 3 で終わる。ページの取得中なら書き込み済みの行は残り、未取得の件数がサマリーに出る（サイトマップの収集中なら CSV は書き出さない）。この場合は `--delay` を短くして再実行せず、時間をおいて `--delay` を長くするか `--limit` で件数を絞って実行し直す。続くならサーバー・WAF の管理者に確認する。
   - 内部アドレスは既定で取得しない。ホスト名を DNS で解決し、プライベート・ループバック・リンクローカル・予約済み・マルチキャスト・未指定のアドレス（IPv4 / IPv6。IPv4 射影の IPv6 も）に当たれば、サイトマップ・子サイトマップ・ページ・robots.txt・リダイレクトのどの段でも取得せず、ページの行は `BLOCKED:private-address` になる（最初のサイトマップが当たれば終了コード 2。子サイトマップが当たれば、その中のページは CSV に出ない）。`--allow-private` は、社内ネットワークにあるステージングの監査とローカルでのテストのときだけ付ける。
   - サイトマップに載っている URL（子サイトマップとページ）のうち、ルートのサイトマップのホスト（リダイレクト後のホストも含む）と違うホストのものは既定で取得せず、ページの行は `SKIPPED:other-host` になる（ローカルファイルのサイトマップは、最初の有効な loc のホストが基準）。比べるのはホスト名だけで、スキームは比べない。渡したサイトマップの URL がリダイレクトすると前後の両方のホストが基準になり、www の有無の混在を見落とすので、リダイレクトしない最終の URL を渡す。別ホストの子サイトマップは取得しないので、その中のページは CSV に出ない（取得しなかった子サイトマップの数はサマリーに出る）。取得するなら `--allow-other-hosts` を付ける。ページのリダイレクトで別ホストに移る場合はたどる（内部アドレスの拒否は適用される）。
   - `--count-mode chars` は日英混在サイトで word_count の単位を文字数にそろえるときに使う。`--ignore-robots` は自社サイトで、robots.txt でブロック中のページの状態も見たいときと、robots.txt が一時的に取れずに `BLOCKED:robots-unreachable` になったときだけ使う。`--user-agent` を変えても Googlebot を名乗らない。先頭はプロダクトトークン（例 `mybot/1.0`）にする。audit.py は robots.txt を、このトークン（デフォルトは `seo-operator-audit`）のグループか `User-agent: *` のグループで判定する。トークンがなければ `*` だけで判定する。
   - 出力 CSV は BOM 付き UTF-8。文字列の列（url・redirect_to・title・desc・canonical）で先頭が `=` `+` `-` `@`、タブ、CR のセルには `'` が付く（Excel で数式として実行されないための無害化。`--no-sanitize` で無効）。title_len・desc_len は元の文字数。pandas で読むときは下の「集計コード」で `'` を外す。
   - クラウドセッションや Cowork で `ERROR:ConnectionError` が並ぶ、またはサイトマップが取れずに終了コード 2 で止まる場合は、ネットワーク制限を疑う。ユーザーの PC で実行して audit.csv をアップロードしてもらう。実行後、標準エラー出力を下の「audit.py の警告・注意の読み方」で確認する。「警告: robots.txt を取得できませんでした」が出ていたら、他のすべてより先に直す課題にする。
   - クライアントサイド描画（CSR）のサイト: ブラウザでは本文が見えるのに、ほぼ全ページで title が空か同じ文言、または word_count が極端に少なければ CSR を疑う。audit.py は JavaScript を実行せず初期 HTML だけを見るので、title・desc・h1_count・word_count は使わず、サーバー応答の status・redirect_to だけを使う。描画後の HTML は、(a) Search Console の URL 検査 →「公開 URL をテスト」→「テスト済みのページを表示」か、(b) JavaScript 描画に対応したクローラーで確かめる。CSR サイトの恒久対策は、サーバーサイド レンダリングか事前レンダリングを開発側と検討する（Google はダイナミック レンダリングを回避策と位置づけている）。初期 HTML に noindex を入れて JavaScript で外す実装は、レンダリング自体が省略されて noindex のまま扱われることがあるので使わない。canonical を JavaScript で別の URL に書き換えない。
3. audit.csv を判定する。下の「audit.csv の判断ルール」で行ごとに判定し、「集計コード」で件数と代表 URL を出す。
   - HTML でない行（PDF など）は title〜word_count が空欄。title・description・h1・分量の判定は h1_count が空欄でない行（HTML を解析した行）に絞る。最終ステータスが `BLOCKED:` か `SKIPPED:` で始まる行は取得していないので、ステータスの集計から外して status ごとに数える。word_count は日本語ページでは本文の文字数、英語ページでは単語数なので、単位の違うページを同じ基準で比べない。
4. ページ インデックス登録レポートを読む。
   - サイトマップ フィルタを「すべての送信済みページ」にして、インデックスさせたい URL の問題に絞る。重複やリダイレクトによる未登録は、正規ページが登録されていれば正常な状態である。
   - 各理由の「ソース」が「ウェブサイト」の問題が修正の対象になる。理由ごとの判断は下の「ページ インデックス登録レポートの理由と対処」を使う。レポートに出る URL の例は最大 1,000 件で、全件ではない。件数の大きい理由は audit.csv と突き合わせて原因のパターン（テンプレート、ディレクトリ）を特定する。
   - 修正後は理由の詳細ページで「修正を検証」を押す。検証は通常 2 週間ほどかかる。
5. robots.txt と noindex を確認する。
   - 最初に、本番に `Disallow: /` や全ページの noindex が残っていないかを見る（ステージングの設定の持ち込み）。主要ページに当てはまれば他のすべてより先に直す。
   - robots.txt が 5xx・429 を返すか、タイムアウトや DNS などのネットワークの問題で取得できないとき、Google はサーバーエラーとして次のように扱う（Google の robots.txt の仕様。429 の扱いは HTTP ステータスコードの説明とクロールの統計情報のヘルプ）。最初の 12 時間はサイトのクロールを止め、robots.txt の取得を試み続ける。取得できないままなら、その後の 30 日間は最後に正常に取得できた robots.txt を使う（キャッシュがなければクロールの制限はないものとみなす）。30 日を過ぎても直らなければ、サイト自体には Google がアクセスできる場合は robots.txt がないものとして扱い、サイトにもアクセスできない場合はクロールを止める（どちらも robots.txt の取得は続ける）。429 以外の 4xx は robots.txt がないもの（全許可）として扱われる。
   - audit.py は robots.txt の取得エラーのとき全拒否として扱い（5xx とネットワークエラーは RFC 9309、429 は Google の仕様に合わせる）、その robots.txt が対象とする URL（スキーム・ホスト・ポートが同じもの）を取得せずに `BLOCKED:robots-unreachable` とし、警告を出す。Google も最初の 12 時間はクロールを止めるので、警告が出たらサーバー・CDN・WAF の設定を最優先で直す。robots.txt は先頭 500 KiB だけが読まれる（Google も audit.py も同じ）。audit.py の `BLOCKED:robots.txt` は Googlebot の判定ではない（手順2の UA の項）。`User-agent: Googlebot` のグループがあるサイトでは結果が Google と違いうるので、robots.txt レポートか URL 検査で確かめる。
   - robots.txt はクロールの制御で、インデックスの制御ではない。ブロックした URL も外部リンク経由でインデックスされることがある（警告「robots.txt によりブロックされましたが、インデックスに登録しました」）。インデックスから外したい URL は robots.txt でブロックせず、meta robots か `X-Robots-Tag` で noindex にする。robots.txt でブロックすると、クローラーはページを取得できず noindex を読めない。
   - robots.txt に書いた `noindex:` 行は 2019年9月1日以降サポートされていない。Google が解釈するフィールドは `user-agent`・`allow`・`disallow`・`sitemap` で、`crawl-delay` は無視される。ページの描画に必要な CSS・JavaScript をブロックしていないかも確認する。
6. サイトマップの衛生を確認する。
   - 載せるのは、正規 URL で、最終ステータスが 200 で、インデックス可能（noindex なし・robots.txt で許可）な URL だけ。audit.csv で条件を外れた URL は、サイトマップから外すか、ページ側を直す。
   - URL は絶対 URL。ファイルは UTF-8。1ファイル 50,000 URL・非圧縮 50MB が上限で、超えたらサイトマップ インデックスで分ける（audit.py は超えたファイルに警告を出す）。インデックスは入れ子にできない（インデックスから別のインデックスを参照すると Search Console でエラーになる）。
   - URL はサイトマップと同じホスト・同じスキームにそろえる。www の有無や http / https が違う URL は、Search Console のサイトマップ レポートで「許可されていない URL」になる。例外はクロス送信（所有権を確認した複数のサイトの URL を1つのサイトマップにまとめて Search Console から送信する方法と、別ホストに置いたサイトマップを各サイトの robots.txt の `Sitemap:` 行で参照する方法）。audit.py の `SKIPPED:other-host` はこの問題の手がかりになる。
   - RSS / Atom のフィードもサイトマップとして送信できるが、含まれるのは最近の URL だけ。全ページの監査にはサイトマップを使う。`lastmod` は本文を実際に更新したときだけ変える。Google は lastmod が一貫して正確だと確認できる場合にだけ使う。全 URL に生成日時を入れる実装は直す。`priority` と `changefreq` は Google が無視する。
   - テンプレート（記事・商品・カテゴリ）ごとに子サイトマップを分けておくと、サイトマップ フィルタで種類別の未登録理由を見られる。
7. URL の重複と正規化を確認する。
   - http / https、www の有無、末尾スラッシュ、大文字小文字、`index.html` の有無は、1つに決めて他を 301 でまとめ、canonical・内部リンク・サイトマップをその形にそろえる。Google は HTTPS 版を優先して正規ページに選ぶ。
   - `utm_` などの計測パラメータや並び替えパラメータの URL は、canonical でパラメータなしの URL を指す。内部リンクにパラメータを付けない。正規化のシグナルは、リダイレクトと rel="canonical" が強く、サイトマップは弱い。robots.txt と noindex は正規化の手段に使わない。
   - EC のファセット ナビゲーション: 検索需要のある組み合わせ（例: カテゴリ × ブランド）だけを、固定の URL を持つインデックス対象のページにする。それ以外は robots.txt でクロールを止めるか、URL フラグメント（`#`）で実装する。パラメータは `&` で区切り、並び順を固定する。結果が0件の組み合わせは 404 を返す。canonical や nofollow は効き目が弱い。
   - ページネーション: 各ページに固有の URL（例 `?page=2`）と自己参照の canonical を付ける。2ページ目以降の canonical を1ページ目に向けない（2ページ目以降にしかない商品や記事へのリンクがたどられにくくなる）。`rel="next"`・`rel="prev"` は Google が使っていない。ページ番号を `#` で表さない。無限スクロールは、各ページにリンクでたどれる URL を用意する。
   - 主要ページで「重複しています。Google により、ユーザーがマークしたページとは異なるページが正規ページとして選択されました」が出たら、2つのページの内容が本当に同じかを確認する。同じなら統合し（鉄則7）、違うなら違いが本文から明確にわかるようにする。
8. 日本語 URL を確認する。Google は ASCII 以外の文字をパーセントエンコード（UTF-8）した URL を推奨している。サイトマップ・canonical・hreflang・内部リンクで、エンコード済みと未エンコード、`%E3` と `%e3` が混在すると、文字列としては別の URL になる。
   - audit.py の canonical_mismatch は、%XX と生の日本語の違い、スキームとホストの大文字小文字、デフォルトポート、フラグメントを同一視して判定する。True の行は、末尾スラッシュ・クエリ・パスの大文字小文字・別パスなど、実際に別の URL を指している。表記の混在はサイトマップと内部リンクの側で起きるので、ページのソースか Screaming Frog のエクスポートで見る。既存の日本語 URL を英字に変えるのは、リダイレクトと内部リンク修正の工数に見合う理由があるときだけにする。
9. hreflang を確認する（多言語・多地域サイトのみ）。各言語版が自分自身を含むすべての版を相互に参照しているか、コードが正しいか（日本語は `ja`、日本向けは `ja-JP`。`jp` は言語コードではない）、該当しない利用者向けに `x-default` があるかを見る。相互参照のない指定は無視される。
10. HTTPS・モバイル・Core Web Vitals を確認する。
    - HTTPS: http の全 URL が https へ 301 しているか、canonical・サイトマップ・内部リンクが https か、混在コンテンツ（https ページ内の http リソース）がないか。
    - モバイル: Google はモバイル版のコンテンツでインデックス登録とランキングを行う。モバイル版とパソコン版で本文・構造化データ・title・meta description・robots meta が同じか、主要コンテンツがユーザー操作（タップやスクロール）でしか読み込まれない実装になっていないかを見る。Search Console のモバイル ユーザビリティ レポートとモバイル フレンドリー テストは 2023年12月に提供終了したため、表示の確認は Lighthouse や Chrome DevTools で行う。
    - Core Web Vitals: 下の「Core Web Vitals のしきい値」で判定する。「Core Web Vitals」レポートは実ユーザーのデータ（過去 28 日、75 パーセンタイル）を URL グループ単位で出す。PageSpeed Insights の実験室データ（Lighthouse）とは値が一致しないことがあるので、判定にはフィールド データを使う。Google はページ エクスペリエンスより関連性の高いコンテンツを優先して表示するとしているため、インデックスの問題より先に置かない。
11. 構造化データのエラーを確認する。「拡張機能」「ショッピング」の各レポートで「無効」の項目を先に見る（警告は後回し）。「解析できない構造化データ」のレポートに出るものは構文エラーで、テンプレート1か所の修正で直ることが多い。どの型を入れるべきか、FAQ などの提供終了した型の扱いは [07-on-page.md](07-on-page.md) を参照する。
12. 優先度を付けて出力する。
    - チェック項目（グループ）ごとに、該当 URL 数、なぜ問題か、直し方をまとめる。同じ原因の URL は1つの施策にまとめ、対象件数と代表 URL を書く。
    - 採点は [00-principles.md](00-principles.md) の基準（影響度 1-5、工数 1-5、優先度 = 影響度 ÷ 工数）に従い、最後に施策表で並べる（鉄則3）。各施策に、どの CV にどう効くかを書く（鉄則2）。下の「技術課題の採点例」を目安にする。採点で迷ったら、404・noindex の誤り・title の欠落と重複の修正を先にする（工数が小さく、主要ページに効くことが多い）。

### 公開前・公開直後の点検

公開前は、ページ インデックス登録レポート、Core Web Vitals のフィールド データ、「修正を検証」が使えない。手順4・10 の Search Console のデータを使う部分は公開後に回す。

- 公開前（ステージング）: テンプレート（トップ・記事・商品・カテゴリなど）ごとに、robots.txt の `Disallow: /`、meta robots と `X-Robots-Tag` の noindex、canonical とサイトマップの URL が本番のドメインになっているかを確認する。canonical が本番を指していれば canonical_mismatch が True になるのが正しい状態なので、canonical 列のホストが本番か、パスがページと対応しているかで判定する。URL にユーザー名・パスワードを含めて渡さない（`http://user:pass@host/` の形は、引数のサイトマップなら取得せずに終了コード 2 で止まり、loc やリダイレクト先なら `SKIPPED:credentials-in-url` になる）。audit.py は Cookie や認証情報を送らないので、Basic 認証などログインが必要な環境は、ブラウザでページのソースを見る（本番に出た後は Search Console の URL 検査も使える）。社内ネットワークにあるステージングは `--allow-private` を付けて実行する。サイトマップの URL がすでに本番のホストなら全件 `SKIPPED:other-host` になるので、ステージングの URL を1行1件で書いたテキストファイルを渡す。表示速度は Lighthouse（Chrome DevTools）の実験室データで確かめる。
- 公開直後: 本番のサイトマップで audit.py を実行し、robots_noindex が True の行、`BLOCKED:robots.txt` の行、canonical がステージングのドメインを指す行を最初に確認する。ステージングの noindex が残ったまま公開されると、ページが検索結果から消える。データが出始めたら、手順1から通常の監査を行う。

### audit.py の限界

- JavaScript を実行しない（CSR のサイトは手順2の方法で確かめる）。Core Web Vitals と表示速度も測らない（手順10）。
- 内部リンクをたどらないので、サイトマップにないページ（載せ忘れ、孤立ページ）を見つけられない。サイト全体をクロールするなら Screaming Frog（無料版は1回 500 URL まで）を使い、そのエクスポートを同じ判断ルールで分析する。サイトマップにない URL のインデックス状況は、手順1の「未送信ページのみ」で見る。
- ログインが必要なページ（Cookie や認証情報を送らない）、hreflang、構造化データは調べない（手順9・11 で別に確認する）。robots.txt の判定に Googlebot 専用のグループを使わない。robots.txt が取れないときは全拒否にするだけで、Google のように最後に取得できた robots.txt を使うことはない（手順5）。

### 大規模サイトの監査

目安は数万 URL 以上か、EC のファセットで URL が増えるサイト。Google のクロール バジェットのガイドは、重複のないページが 100 万以上で週1回ほど更新されるサイト、1 万以上で毎日更新されるサイト、URL の大部分が「検出 - インデックス未登録」のサイトを主な対象にしている（大まかな目安とされている）。全件を audit.py で取るより、次の組み合わせで見る。

- URL の型ごとの抜き出し: URL をテンプレート（記事・商品・カテゴリ・ファセット・タグなど）の型に分け、型ごとに数件ずつ（流入の多いページと、無作為に選んだページ）を監査する。型ごとに子サイトマップが分かれていれば、それぞれ `--limit` で実行する。分かれていなければ、抜き出した URL を1行1件のテキストファイルにして audit.py に渡す。問題は型ごとに1つの施策にまとめる。
- クロールの統計情報: Search Console →「設定」→「クロールの統計情報」。クロール リクエストの合計数、平均レスポンス時間、ホストのステータス（robots.txt の取得・DNS の解決・サーバー接続）と、レスポンス別・ファイル形式別・目的別（検出 / 更新）・Googlebot の種類別の内訳を見られる。ルートレベルのプロパティ（ドメイン プロパティか、ルートの URL プレフィックス プロパティ）でだけ使え、ヘルプでは 1,000 ページ未満のサイトには不要とされている。5xx やリダイレクトの割合、内訳のサンプル URL がファセットやパラメータ付き URL に偏っていないかを見る（サンプル URL は代表例で、全件ではない）。
- アクセスログ: Googlebot のリクエストを URL の型・ステータスコード・日付で集計し、CV につながる型が取られているか、ファセット・パラメータ付き URL・リダイレクト・404 にクロールが偏っていないかを見る。User-Agent は偽装できるので、本物の Google のクローラーかは、IP を逆引き DNS（`host` コマンド）してドメインが googlebot.com・google.com・googleusercontent.com のどれか（Googlebot は googlebot.com）で、そのホスト名の正引きが元の IP に戻るかで確かめるか、Google が公開する IP の範囲（一般的なクローラーは common-crawlers.json）と照合する。ログとクロールの統計情報の数は少し違うことがある。
- 一括データエクスポート（BigQuery）: Search Console →「設定」→「一括データのエクスポート」。UI の1,000行の制限を受けずに、ページ別の表示回数・クリック数を型ごとに集計できる。設定した後のデータだけが蓄積される（注意点は [10-gsc-growth.md](10-gsc-growth.md)）。

### audit.py の警告・注意の読み方

標準エラー出力には、CSV の列に出ない問題が出る。表示の文言は抜粋。同じ注意が複数のページに出ていれば、テンプレートの修正を1つの施策にする。

| 表示（抜粋） | 意味 | 対処 |
|---|---|---|
| `警告: robots.txt を取得できませんでした`（5xx・429・タイムアウトなど） | audit.py は、その robots.txt が対象とする URL を取得せず、`BLOCKED:robots-unreachable` にした。Google も最初の 12 時間はクロールを止め、その後 30 日間は最後に取得できた robots.txt を使う（30 日以降は手順5） | 最優先。サーバー・CDN・WAF を確認し、robots.txt レポートで取得状況を見る。直ったら audit.py を再実行する |
| robots.txt の読み込みで「500 KiB を超えた部分は無視」 | 先頭 500 KiB より後のルールは Google も読まない | robots.txt を短くまとめる |
| `中断しました: 429 / 503 が 5 回続いたため、…`（未取得の件数）、`中断しました（サイトマップの収集中）: 429 / 503 が …`（どちらも終了コード 3） | サーバーか WAF が audit.py のリクエストを制限している。audit.csv は中断までの分だけ（サイトマップの収集中に止まったら CSV はない） | 手順2の 429 / 503 の項に従う。Googlebot にも同じ応答が返っていないかを、クロールの統計情報のレスポンス別の内訳で確かめる |
| `警告: URL が … 件あり、Google の上限（1 ファイル 50,000 件）を超えています`、`警告: 展開後の大きさが … バイトあり、Google の上限（展開後 50MB …）を超えています`（件数はサマリー） | Google の上限を超えている。audit.py は安全のための上限 100MB まで読み続ける | サイトマップ インデックスで複数のファイルに分ける（手順6） |
| `サイトマップを取得しません。…内部アドレス（…）に解決されます`、`robots.txt を取得しません。…`、ページの下の `内部アドレス（…）に解決されるため取得しませんでした` | 内部アドレスの拒否で取得しなかった。取得しなかった子サイトマップの中のページは CSV に出ない（取得しなかったサイトマップの数はサマリーに出る） | 下の「audit.csv の判断ルール」の `BLOCKED:private-address` と同じに扱う |
| `警告: サイトマップのホスト（…）と別のホストの URL が … 件あります`、`サイトマップと別のホストの子サイトマップは取得しません` | ページの行は `SKIPPED:other-host` になっている。取得しなかった子サイトマップの中のページは CSV に出ない | 下の「audit.csv の判断ルール」の `SKIPPED:other-host` と同じに扱う |
| `注意: サイトマップを取得しません。…認証情報（userinfo）が含まれます`、`注意: URL に認証情報（userinfo）を含む子サイトマップは取得しません`、サマリーの `URL に認証情報（userinfo）を含むため取得しなかった` | サイトマップやリダイレクト先に `user:pass@` の形の認証情報が載っている（表示は伏せ字）。取得していない | 下の「audit.csv の判断ルール」の `SKIPPED:credentials-in-url` と同じに扱う |
| `警告: サイトマップインデックスが別のサイトマップインデックスを参照しています（入れ子）` | audit.py はたどるが、Google は入れ子に対応せず、Search Console でエラーになる | インデックスからは子サイトマップだけを参照する |
| `XML が途中で切れているか壊れています`、`サイトマップの文字コードが … です`、スキップした loc の件数 | 壊れる前までの URL、UTF-8 に変換した結果、http / https 以外や空の loc を除いた結果で続行している | サイトマップの生成側を直す課題にし、Search Console のサイトマップ レポートでも確認する |
| `<head> に置けない要素 … より後にある rel="canonical" を無視しました`、`<body> 内の rel="canonical" を無視しました`、`<head> に置けない要素 … があります` | Google は `<head>` 内の canonical だけを受け付け、`<head>` に置けない要素があるとそこで `<head>` が終わったとみなす。無視した canonical は CSV で空欄になる | canonical を `<head>` の前のほうへ移すか、`<head>` に置けない要素（img・iframe・div など）を `<body>` へ出す |
| `<title> が n 個あります`、`<meta name="description"> が n 個あります`、異なる rel="canonical" が複数、`HTML と Link ヘッダーで canonical が異なります` | テンプレートやプラグインが重複して出力している。CSV には最初の値が入る | 出力元を1つにする |
| `title にタグのような文字列が含まれています` | `</title>` の閉じ忘れか、`<` のエスケープ漏れの可能性 | HTML を確認する |
| `… の charset（…）では読めないため … で読みました` など文字コードの注意 | Content-Type の charset か meta charset が実際の文字コードと違う。ブラウザでは文字化けしている可能性がある | サーバー設定かテンプレートの charset を直す |
| `… ですが Location ヘッダーがない（空の）ため、リダイレクト先をたどれません` | リダイレクト先のないリダイレクト | リダイレクト規則を直す |

### audit.csv の判断ルール

| 条件 | 判断 | 対処 |
|---|---|---|
| 最終ステータス（status の最後の値）が 404 / 410 | サイトマップに載せてはいけない URL | 削除済みならサイトマップから外す。移転したなら移転先へ 301 し、サイトマップも移転先にする |
| 最終ステータスが 5xx・429、`ERROR:Timeout` | 一時的な障害か恒常的な問題か不明。429 / 503 は audit.py のリクエストへの制限のこともある | `--timeout 30` で再実行する（429 / 503 なら時間をおいて `--delay` を長くする）。再現すればサーバー担当へ。5xx・429 が続くと Google はクロールを減らし、長引けばインデックスから外れる |
| `ERROR:SSLError` / `ERROR:TooManyRedirects` | 証明書の問題 / リダイレクトのループ | 証明書の期限・中間証明書を確認する / リダイレクト規則を確認する |
| `BLOCKED:robots.txt` がサイトマップにある | サイトマップと robots.txt が矛盾している（audit.py の UA での判定） | インデックスさせたいなら robots.txt を直す。させたくないならサイトマップから外す。Googlebot 専用のグループがあれば robots.txt レポートか URL 検査で確かめる |
| status が `BLOCKED:robots-unreachable` | その URL に適用される robots.txt が 5xx・429・タイムアウトなどで取れず、ページを取得しなかった | robots.txt を直すのが最優先（上の警告の表と手順5）。自社サイトで一時的な障害なら、`--ignore-robots` を付けて取り直す |
| status が `SKIPPED:other-host` | サイトマップと違うホストの URL が載っている（取得していない） | サイトマップの問題として扱う。www の有無の違い、ステージングや別のサブドメインのホストが混ざっていないかを見て、サイトマップと同じホストの正規 URL にそろえる。http / https の違いはホストの違いではないので、この status とは別に url 列のスキームで確かめる（Search Console ではどちらも「許可されていない URL」になる）。意図したクロス送信（手順6）なら問題ない。中身を監査するなら `--allow-other-hosts` で取り直す |
| status が `SKIPPED:credentials-in-url` | loc かリダイレクト先の URL にユーザー名・パスワード（`http://user:pass@host/` の形）が含まれている（取得していない。URL は伏せて出力される） | サイトマップの生成設定かリダイレクト規則を直し、認証情報を含む URL を載せない。公開されていた認証情報は変更する。ログインが必要な環境は、ページのソースか URL 検査で見る（「公開前・公開直後の点検」） |
| 最終ステータスが `BLOCKED:private-address` | ホスト名が内部アドレスに解決された（取得していない）。リダイレクト先で当たった場合は redirect_to にその URL が入る | 公開サイトなら、サイトマップやリダイレクト先に社内やステージングのホスト名が入っていないか、DNS の設定を確かめる。社内ネットワークや VPN・プロキシを通した環境から実行すると、本番のホスト名が内部アドレスに解決されることがあるので、別のネットワークで実行し直して確かめる。社内のステージングの監査なら `--allow-private` を付ける |
| status が `301>200` のように1段のリダイレクト | サイトマップに移転前の URL が残っている | サイトマップと内部リンクを redirect_to の URL に置き換える |
| `>` が2つ以上（2段以上のリダイレクト） | リダイレクトチェーン | 最初の URL から最終 URL へ直接リダイレクトさせる。Google は最大 10 回までたどるが、直接の転送を推奨している |
| 恒久的な移転なのに 302 / 307 | 一時的な転送は移転先を正規とするシグナルが弱い | 301 / 308 に変える |
| robots_noindex が True なのにサイトマップにある | どちらかが意図と違う | 主要ページなら noindex を外す（影響度高）。インデックス不要ならサイトマップから外す |
| canonical_mismatch が True | 別 URL を正規と宣言している（エンコードの違いは audit.py が除いている） | 重複ページなら、サイトマップには正規 URL を載せる。大半のページが同じトップや1ページ目を指していればテンプレートの不具合。正規先自体が 200 でない、または noindex なら正規先を直す |
| canonical が空欄（HTML の行） | 正規 URL の指定がない、または置き場所のせいで無視された | 標準エラーに canonical を無視した注意があれば置き場所を直す。なければ自己参照の canonical を入れる（Google も推奨）。重複が起きていなければ優先度は低い |
| title_len が 0 / title が他ページと重複 | title なし / 同じ title の複数ページ | 文面は 07 で作る。同じ title が同じ検索意図の複数ページなら、統合を先に検討する（鉄則7） |
| title_len が極端（日本語ページで 10 未満か 45 超を候補とする運用上の目安） | 短すぎ / 長すぎの候補 | title_len は Python の `len()` の文字数で、全角換算ではない。07 の方法で全角換算に直してから判断する |
| desc_len が 0 | meta description なし | 07 で作る。Google は本文からスニペットを作るので、title なしより優先度は下げる |
| desc が他ページと重複 | 同じ meta description の複数ページ | テンプレートの既定文が入っていないかを見る。文面は 07 でページごとに作る |
| h1_count が 0 | 主見出しがない、またはロゴ画像やデザイン用の要素に置き換わっている | テンプレートを直す |
| h1_count が 2 以上 | ヘッダーのロゴなどが h1 になっている例が多い | Google は見出しの数に理想値はないとしているので、単独の優先度は低い。テンプレート修正のついでに1つにそろえる |
| word_count が同じ階層の中央値の 30% 未満（運用上の目安） | 薄いページの候補。日本語ページは文字数で、サイト内の分布から判断する | お問い合わせ・規約・プライバシーポリシー・カート・検索結果などのユーティリティ系ページは対象外。分量だけでは順位は決まらないので、一覧や入口として役割があるかを見て、役割がなければ統合・加筆・noindex のどれかを選ぶ（鉄則7） |
| 最終ステータスが 2xx で h1_count・word_count が空欄 | PDF など HTML 以外。canonical は Link ヘッダー、robots_noindex は `X-Robots-Tag` から記録されている | 意図して載せているなら問題なし。robots_noindex が True ならサイトマップから外す。canonical_mismatch が True なら、Link ヘッダーが正規にしたい HTML ページを指しているか確認する |

### 集計コード（pandas）

audit.csv の列名は `scripts/audit.py` の仕様どおり。True / False は文字列として読む。

```python
import pandas as pd

df = pd.read_csv("seo/audit.csv", encoding="utf-8-sig", dtype=str, keep_default_na=False)
# 無害化で先頭に付いた ' を外す（--no-sanitize で取った CSV なら不要）
for c in ["url", "redirect_to", "title", "desc", "canonical"]:
    df[c] = df[c].str.replace(r"^'(?=[=+\-@\t\r])", "", regex=True)
for c in ["title_len", "desc_len", "h1_count", "word_count"]:
    df[c] = pd.to_numeric(df[c], errors="coerce")
html = df["h1_count"].notna()  # HTML を解析した行（PDF などは空欄）
df["final_status"] = df["status"].str.split(">").str[-1]
df["hops"] = df["status"].str.count(">")
df["section"] = df["url"].str.extract(r"^https?://[^/]+(/[^/?#]*)", expand=False).fillna("/")
fetched = ~df["final_status"].str.startswith(("BLOCKED:", "SKIPPED:"))  # 取得した行（BLOCKED / SKIPPED 以外）
print(df.loc[~fetched, "final_status"].value_counts())  # BLOCKED:robots.txt / SKIPPED:other-host など

checks = {
    "最終ステータスが200以外": fetched & (df["final_status"] != "200"),
    "リダイレクト2段以上": df["hops"] >= 2,
    "noindexなのにサイトマップにある": df["robots_noindex"] == "True",
    "canonical不一致": df["canonical_mismatch"] == "True",
    "titleなし": html & (df["title_len"] == 0),
    "descriptionなし": html & (df["desc_len"] == 0),
    "h1が1個でない": html & (df["h1_count"] != 1),
}
print(pd.Series({k: int(v.sum()) for k, v in checks.items()}))

# 薄いページ候補: 同じ第1階層の中央値の30%未満。ユーティリティ系のパスはサイトに合わせて書き換える
utility = df["url"].str.contains(r"/(?:contact|inquiry|privacy|terms|policy|cart|search|login)", regex=True)
med = df["word_count"].where(html).groupby(df["section"]).transform("median")
print(df.loc[html & ~utility & (df["word_count"] < med * 0.3), ["url", "section", "word_count"]])

# title と meta description の重複
for col in ["title", "desc"]:
    dup = df[html & (df[col] != "")].groupby(col)["url"].agg(["count", list])
    print(dup[dup["count"] > 1].sort_values("count", ascending=False).head(20))
```

### ページ インデックス登録レポートの理由と対処

表記は Search Console ヘルプの日本語版に合わせた。画面上の表記はヘルプと少し違うことがある（例: 画面では「noindex タグによって除外されました」）。照合に迷ったら英語版の表記と見比べる。

| 理由（ヘルプの表記） | 英語版ヘルプの表記 | 意味 | 判断と対処 |
|---|---|---|---|
| サーバーエラー（5xx） | Server error (5xx) | クロール時に 5xx が返った | 主要ページなら最優先。サーバーの負荷・タイムアウトを確認する |
| リダイレクト エラー | Redirect error | チェーンが長すぎる、ループ、空の URL など | audit.csv の status で経路を確認し、直接の転送に直す |
| URL が robots.txt によってブロックされています | URL blocked by robots.txt | robots.txt でクロール禁止 | 意図どおりなら対処不要。インデックスさせたい URL なら robots.txt を直す |
| URL に noindex が指定されています | URL marked 'noindex' | noindex を検出した | 意図どおりなら対処不要。主要ページなら noindex を外し、URL 検査の「公開 URL をテスト」で消えたことを確認する |
| ソフト 404 | Soft 404 | 200 を返すが中身が「見つからない」ページと判定された | 存在しないページは 404 / 410 を返す。有効なページなら、本文が空に近くないか、描画に必要なリソースが読めているかを確認する |
| 未承認のリクエスト（401）が原因でブロックされました | Blocked due to unauthorized request (401) | 認証が必要 | 公開ページなら認証を外す。会員ページならサイトマップから外す |
| 見つかりませんでした（404） | Not found (404) | 404 が返った | 代わりのない削除なら問題ない。移転したなら 301。サイトマップや内部リンクに残っていれば外す |
| アクセス禁止（403）が原因でブロックされました | Blocked due to access forbidden (403) | 403 が返った | WAF や海外 IP の遮断で Googlebot を止めていないか確認する |
| 他の 4xx の問題が原因で、URL がブロックされました | URL blocked due to other 4xx issue | 上記以外の 4xx | URL 検査で個別に確認する |
| クロール済み - インデックス未登録 | Crawled - currently not indexed | クロールしたが登録しなかった | 再送信では解決しない。主要ページなら、同じ意図の既存ページとの重複、内容の薄さ、内部リンクの少なさを確認し、統合か加筆をする（鉄則7） |
| 検出 - インデックス未登録 | Discovered - currently not indexed | URL は知っているがまだクロールしていない | 新しいページなら待つ。大量にあるなら、ファセットなど低価値 URL の量産でクロールが追いついていないか、サーバー応答が遅くないかを確認する |
| 代替ページ（適切な canonical タグあり） | Alternate page with proper canonical tag | 正規ページが別にあり、指定も正しい | 対処不要 |
| 重複していますが、ユーザーが正規ページとして選択していません | Duplicate without user-selected canonical | canonical の指定がなく、Google が別 URL を正規に選んだ | URL 検査で Google が選んだ正規 URL を確認し、その URL でよければ canonical を明示する |
| 重複しています。Google により、ユーザーがマークしたページとは異なるページが正規ページとして選択されました | Duplicate, Google chose different canonical than user | 指定した canonical を Google が採用しなかった | 指定先と内容が似ているか、指定先が 200 でインデックス可能かを確認する。手順7の最後の項目を参照 |
| ページにリダイレクトがあります | Page with redirect | リダイレクト元の URL | 通常は対処不要。サイトマップや内部リンクに残っていれば最終 URL に置き換える |
| （警告）robots.txt によりブロックされましたが、インデックスに登録しました | Indexed, though blocked by robots.txt | ブロック中でもリンク経由で登録された | 外したいなら robots.txt のブロックを解除して noindex を付ける |
| （警告）コンテンツのない状態でページがインデックスに登録されています | Page indexed without content | 登録されたが内容を読めなかった | クローキングや Google が読めない形式になっていないか確認する |

### Core Web Vitals のしきい値

「Core Web Vitals」レポートの区分（過去 28 日間のページ読み込みの 75% での値）。CV ページを含む URL グループの「低速」を先に扱い、原因の調査と改善は、代表 URL を PageSpeed Insights にかけて開発側と進める。

| 指標 | 良好 | 改善が必要 | 低速 |
|---|---|---|---|
| LCP（Largest Contentful Paint） | 2.5 秒以下 | 4 秒以下 | 4 秒超 |
| INP（Interaction to Next Paint） | 200 ミリ秒以下 | 500 ミリ秒以下 | 500 ミリ秒超 |
| CLS（Cumulative Layout Shift） | 0.1 以下 | 0.25 以下 | 0.25 超 |

| ヘッダーのロゴが h1 | 1 | テンプレート修正で 1〜2 |

## 6. よくある失敗

- robots.txt でブロックしたうえで noindex を付ける: クローラーがページを取得できず noindex を読めない。外したい URL は robots.txt で許可し、noindex だけで外す。
- audit.csv だけを見て、標準エラー出力の警告を読まない: 無視された canonical は CSV の列に出ない。robots.txt の取得失敗も、CSV では `BLOCKED:robots-unreachable` としかわからず、エラーの種類は警告にだけ出る。実行時の出力を保存し、「audit.py の警告・注意の読み方」で確認する。
- 未登録の URL をすべてエラーとして報告する: 重複・代替・リダイレクト元の未登録は正常な状態である。「すべての送信済みページ」に絞り、インデックスさせたい URL の問題だけを施策にする。
- 「クロール済み - インデックス未登録」をインデックス登録のリクエストで解決しようとする: 再送信の必要はないとヘルプにもある。重複・内容・内部リンクを見直し、統合か加筆をする。
- CSR サイトで audit.csv の空欄をそのまま「title なし」と報告する: audit.py は JavaScript を実行しない。URL 検査の「テスト済みのページを表示」で描画後の HTML を確認してから判断する。
- ステージングの `Disallow: /` や noindex を本番に持ち込む: 公開直後とリニューアル直後は、最初に robots.txt と主要ページの meta robots を確認する（「公開前・公開直後の点検」）。
- word_count だけで薄いページを決める: 単位の違うページ（文字数と単語数）や、お問い合わせ・規約などのユーティリティ系を同じ基準で比べない。同じ階層・同じ言語の中で比べ、役割を見てから判断する。
- Lighthouse の点数で Core Web Vitals を判定する: 判定には Search Console のフィールド データを使う。実験室データは原因の調査に使う。
- `--limit` で取った先頭の数百件を、サイト全体の傾向として報告する: サイトマップの並び順によって一部の型に偏る。子サイトマップごとか URL の型ごとに抜き出して監査し、報告に監査の範囲を書く。
- 他社サイトに `--delay` を短くして実行する、Googlebot を名乗る: 自社サイトか許可を得たサイトだけを対象にし、デフォルトの間隔と UA で実行する。
- 施策を URL 1件ずつに分けて並べる: 同じテンプレート・同じ規則が原因なら1つの施策にまとめ、対象件数と代表 URL を書く。
