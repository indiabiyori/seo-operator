# 10 Search Console 分析と改善

Search Console のエクスポートと付属スクリプトで、順位8〜20位・低CTR・下落の3種類の伸びしろを見つけ、打ち手と効果測定までを決めるための手順。

## 1. 目的

- 新しいページを作るより少ない工数で成果が出やすい、既存ページの改善候補を見つける。
- 順位8〜20位・低CTR・下落の3つの分析を月1回行い、候補ごとに原因の当たりを付けて、title の修正・リライト・内部リンク・技術的な修正のどれを行うかを決める。
- 変更を反映日とともに記録し、反映後の実測で効果を判定する。効果を予測で断定しない。改善対象が見つからなければ、施策を無理に作らない。
- 目的は CV につながる流入を増やすこと（鉄則2）。クリック数が増えても CV に関係しないクエリは優先度を下げる。

## 3. 手順

### 手順1 期間を決めてエクスポートする

- 3つの分析は月1回、同じ手順で行う。期間は直近3か月を使う（週ごとの揺れがならされ、最近の状態も反映される）。
- 期間の終了日は、今日から3日以上前にする。データは通常2〜3日で揃い、最新の日は暫定値で後から変わることがある。
- Search Console の日付は太平洋時間（PT）で区切られている。日本時間とは日付の境界がずれるので、日単位の比較では前後1日の誤差を見込む。
- 下落の分析は、直近3か月と前年同期の3か月を比べる（季節性を除くため）。前年のデータがないときだけ、直前の同じ長さの期間と比べる。どちらも期間ごとに1回ずつエクスポートする。比較表示のままのエクスポートは列名に期間のラベルが付き、decay.py が受け付けない。
- 日数は7の倍数（28日、91日など）にして曜日の構成をそろえる。16か月より前のデータが必要になりそうなら、API か BigQuery で定期的に保存しておく。
- 検索タイプは「ウェブ」を使う。英語版ヘルプでは「ウェブ」が Web: text-based と Web: multimodal に分けて記載されている。画面で分かれて表示される場合は、両方を含めて見る。AI による概要・AI モードからのクリックは「ウェブ」に含まれ、分けて見られない。表示回数だけは「生成 AI パフォーマンス レポート（検索）」で、ページ・国・デバイス・日付別に見られる（2026年8月31日に全サイトへ提供。クエリ別には見られない。同じデータは「ウェブ」にも含まれる。詳細は [09-ai-search.md](09-ai-search.md) の「計測の方法」）。
- Search Console が集計するのは Google 検索での表示とクリック。Yahoo! JAPAN 経由の検索を含むかどうかは公式に明記がないため、Yahoo! JAPAN からの流入は GA4 の参照元（`yahoo.co.jp` など）で別に確認する。
- UI のエクスポートは最大1,000行。画面で「~」「-」と表示される値は、ファイルでは 0 になる。付属のスクリプトは掲載順位 0 を値なしとして扱う（striking_distance.py と low_ctr.py はその行を除外し、decay.py は順位の判定に使わない）。1,000行を超える場合の入手方法:
  - Search Console API: 1回のリクエストで最大25,000行（`rowLimit`）、`startRow` でページ送りする。1日・1サイト・1検索タイプあたり50,000行が上限で、すべての行が返る保証はない。クエリ×ページの組み合わせも取れる。
  - Data Studio（旧 Looker Studio）の Search Console コネクタ: API と同じ上限。
  - BigQuery への一括データエクスポート: 行数の上限を受けない。設定した後のデータだけが蓄積され、過去分はさかのぼらない。Google Cloud の利用料金の対象になる。付属のスクリプトに渡す前に、次の点に注意して集計する（手順2）。
    - 同じキーの行が1行にまとまっている保証はないので、必ず `SUM` で合計する。期間は `data_date`（太平洋時間）で絞り、「ウェブ」に合わせるなら `search_type = 'WEB'` で絞る。
    - UI のクエリ別の表に当たるのはプロパティ単位の `searchdata_site_impression`、ページ別の表に当たるのは URL 単位の `searchdata_url_impression`。
    - 掲載順位の列は、最上位を 0 とした順位の合計で入っている。平均掲載順位は `SUM(sum_top_position) / SUM(impressions) + 1`（URL 単位のテーブルでは `sum_position`）で求める。
    - 匿名化されたクエリは、クエリの値がない行（`is_anonymized_query` が true）として入る。クエリ別に集計するときは除く。
    - 列名を `query`（URL 単位なら `url`）・`clicks`・`impressions`・`position` にすると、付属のスクリプトがそのまま読める。
- 匿名化されたクエリ（2〜3か月の間に数十人程度を超えるユーザーが検索していないクエリ）は、プライバシー保護のため表に出ない。
  - 表の行の合計はグラフの合計より小さくなる。クエリでフィルタすると匿名化分は除かれる。サイト全体の増減はグラフの合計かページ別のデータ（1,000行の切り捨てに注意）で判断し、クエリ別の合計では判断しない。
  - クエリ別のデータで表示回数が 0、または行がないことを、「検索結果に表示されていない」「インデックスされていない」と読まない。インデックスの有無は URL 検査か、ページ インデックス登録レポート（「インデックス作成」→「ページ」）で確かめる。
  - 小規模サイトやロングテール中心のサイトほど、匿名化で隠れる割合が大きくなりうる。

### 手順2 スクリプトを実行する

先に `python3 <スキルのディレクトリ>/scripts/<名前>.py --help` で引数を確認する。以下は作業フォルダで実行する例で、ZIP を展開した CSV をユーザーに `seo/data/` に置いてもらった場合のパスにしている。作業フォルダの直下など別の場所にあるときは、そのパスをそのまま渡す（移動もコピーもしない）。出力は `seo/output/` に書く（スキルのフォルダには書かない）。スクリプトは出力先のフォルダを作らないので、先に作る。Search Console の ZIP は、期間やフィルタを変えても中のファイル名が同じ（`クエリ.csv`、`ページ.csv` など）なので、2つ以上の CSV を同じ `seo/data/` に置くと上書きされる。そのときは、期間やフィルタがわかる名前に変えてから置いてもらう（下の decay.py の例）。1つだけなら名前はそのままでよい。

```bash
mkdir -p seo/output

# 順位8〜20位で表示回数100以上（既定値）のクエリ。ブランド名クエリを除く
python3 <スキルのディレクトリ>/scripts/striking_distance.py seo/data/クエリ.csv -o seo/output/striking.csv --exclude-regex "ブランド名|brand"

# 平均掲載順位5位以内で、同じ CSV の同じ順位帯の実績CTRの半分に届かないページ
python3 <スキルのディレクトリ>/scripts/low_ctr.py seo/data/ページ.csv -o seo/output/low_ctr_pages.csv --max-pos 5

# 前年同期と比べてクリック数が30%以上（既定値）減ったページ
python3 <スキルのディレクトリ>/scripts/decay.py --current seo/data/ページ_直近3か月.csv --previous seo/data/ページ_前年同期.csv -o seo/output/decay.csv
```

- 3つとも、UI のエクスポート（ZIP を展開した CSV）と、API・Data Studio・スプレッドシート経由の CSV を読める。英語・日本語のどちらの列名の表記（ファイル名・列名は画面の言語や時期で変わることがある）、UTF-8 / cp932 / UTF-16、カンマ・タブ・セミコロン区切り、小数点がカンマの表記にも対応する。ZIP のまま渡すと、展開するよう表示して終了コード 2 で止まる。
- 3つともファイル全体をメモリに読み込む。UI のエクスポート（1,000行）や API の数万〜数十万行はそのまま渡してよい。BigQuery の一括データエクスポートのような数百万行のデータは、先に BigQuery や DuckDB などで期間とキー（クエリ・URL）ごとに集計し、1キー1行の CSV にしてから渡す（集計の注意は手順1）。
- 共通の引数: `--key {auto,query,page}`（auto は query 列があれば query）、`--ctr-unit {auto,percent,ratio}`、`--include-regex` / `--exclude-regex`（キー列に適用）、`--top N`（0 は全件）、`-o/--output`、`--no-sanitize`。サマリーと CTR の単位の判定結果は標準エラーに出る。`low_ctr.py` の `--ratio` は 0 より大きく 1 以下で指定する。
- 出力先によって形式が違う。
  - `-o` のファイル: BOM 付き UTF-8。`query` / `page` 列で先頭が `=` `+` `-` `@`・タブ・CR のセルの前に `'` を付ける（CSV インジェクション対策。「-20度 寝袋」のような正当なクエリにも付く）。Excel で開くならこちらを使う。
  - 標準出力: BOM なしの UTF-8 で、`'` は付けない。Claude や他のツールが読むための経路で、リダイレクトしたファイルを Excel で開くと文字化けすることがある。
  - `-o` のファイルを pandas などで読むときは、先頭の `'` を除くか、`--no-sanitize` を付けて出し直す。クエリを別の CSV と突き合わせるときに食い違いの原因になる。
- `-o` に入力ファイルと同じパスは指定できない（終了コード 2）。必須の列がない CSV は、見つかった列名と受け付ける列名を表示して終了コード 2 で止まる。同じ項目の列が2つある CSV も終了コード 2 で止まる（CTR の列だけは、重複していれば使わずに「クリック数 ÷ 表示回数」で計算する）。どちらの場合も、エクスポートをやり直すか、使う列だけを残してもらう。
- ブランド名の除外には、表記ゆれをすべて入れる。例（架空）: `--exclude-regex "example|エグザンプル|えぐざんぷる|example\s?shop"`。照合は英字の大文字・小文字を区別せず、全角・半角をそろえた値にも行われるが、ひらがなとカタカナ、略称、スペースの有無は自動ではそろわないので、それぞれ書く。Search Console のブランド / 非ブランドのクエリフィルタ（最上位のプロパティで、クエリと表示回数が十分なサイトだけ）が使えるなら、非ブランドに絞ってからエクスポートしてもよい。

### 手順2 補足: 出力列の意味

striking_distance.py（`position` が `--min-pos`〜`--max-pos`、`impressions` が `--min-impressions`（既定 100）以上の行。`est_extra_clicks` の降順、同じ値なら `impressions` の降順）

| 列 | 意味 |
|---|---|
| `query` または `page` | キー列。CSV に両方の列があれば、キーにしなかった列も残る |
| `clicks` / `impressions` | 期間中の合計 |
| `ctr` / `ctr_pct` | CTR（比率、小数第4位）と、その百分率表示 |
| `position` | 平均掲載順位（そのクエリで表示された自サイトの最上位の結果の平均） |
| `est_extra_clicks` | 同じ CSV で掲載順位が `--target-max-pos`（既定 3）以下の行の「合計クリック数 ÷ 合計表示回数」を目標CTRとし、`表示回数 × max(0, 目標CTR − 現在のCTR)` で出した概算。該当行がないか、その合計表示回数が100未満なら空欄 |

low_ctr.py（`position` が `--max-pos`（既定 10）以下、`impressions` が `--min-impressions`（既定 100）以上、`ctr` が `expected_ctr × --ratio`（既定 0.5）未満の行。`lost_clicks` の降順）

| 列 | 意味 |
|---|---|
| `bucket` | 平均掲載順位の区間。`[1,2)` `[2,3)` `[3,4)` `[4,6)` `[6,8)` `[8,11)` `[11,16)` `[16,21)` `[21,31)` `[31,∞)` に分ける（`[4,6)` は 4.0 以上 6.0 未満） |
| `expected_ctr` | 同じ CSV（絞り込み後）の、表示回数が `--baseline-min-impressions`（既定 10）以上の行で計算した、その区間の「合計クリック数 ÷ 合計表示回数」。行数が `--min-bucket-rows` 未満の区間は空欄で、その区間の行は抽出されない。`--benchmark` を指定するとその CSV の値を使う |
| `ctr_vs_expected` | `ctr ÷ expected_ctr`。1より小さいほど期待を下回る |
| `lost_clicks` | `impressions × (expected_ctr − ctr)`。期待CTRに届いていれば得られたクリック数の概算 |

decay.py（前期のクリック数が `--min-clicks` 以上で、減少数が `--min-drop-clicks` 以上、減少率が `--min-drop-pct`（既定 30）以上の行。`clicks_diff` の昇順）

| 列 | 意味 |
|---|---|
| `clicks_prev` / `clicks_cur` / `clicks_diff` / `clicks_change_pct` | 前期・今期のクリック数、差（今期 − 前期）、変化率（%） |
| `impressions_prev` / `impressions_cur` / `impressions_change_pct` | 表示回数と変化率（%） |
| `ctr_prev` / `ctr_cur` | CTR（比率） |
| `position_prev` / `position_cur` / `pos_diff` | 平均掲載順位と差（今期 − 前期。正の値が悪化） |
| `diagnosis` | 上から順に判定したラベル: 消失（今期のデータなし）→ 順位低下（`pos_diff` が `--pos-threshold` 以上）→ 需要減（表示回数の減少率が `--impr-drop-pct` 以上）→ CTR低下（CTR の減少率が `--ctr-drop-pct` 以上）→ 複合要因 |

- decay.py の `page` の照合: スキーム・ホスト名の大文字・小文字と、パーセントエンコードの表記（`%E9%87%8E` と「野」）の違いだけを同じ URL とみなす。パスの大文字・小文字と末尾の `/` の違いは別の URL として扱う。前期だけ・今期だけの URL がこの違いだけで対応する場合は標準エラーに注意が出るので、その「消失」は URL の変更として手順5で確かめる。出力のキーは今期の表記。
- `est_extra_clicks`・`expected_ctr`・`lost_clicks` は、自サイトの実績 CTR を当てはめた目安であり、予測ではない。クエリごとの SERP 機能や競合の強さは反映されない。候補の並べ替えに使い、関係者に「○クリック増える」と約束する根拠にしない（鉄則1）。
- `diagnosis` は当たりを付けるためのラベルで、原因の断定ではない。
- `--benchmark` に渡す CSV は、自サイトの過去の実績など出どころを説明できる値にする。出典のない業界平均の CTR を作って渡さない（鉄則1）。

### 手順2 補足: 閾値の調整

| 状況 | 調整 |
|---|---|
| 小規模サイトで候補が0件か数件 | striking_distance.py の `--min-impressions` を段階的に下げる（例: 50 → 30 → 10）。low_ctr.py の `--min-impressions` を 30〜50 に、decay.py の `--min-clicks` と `--min-drop-clicks` を下げる。表示回数が少ない行は誤差が大きいので、影響度を低めに付け、使った値を報告に書く |
| 大規模サイトで候補が多すぎる | `--min-impressions` を上げるか、`--top 50` で上位だけを見る |
| `est_extra_clicks` が空欄になる | 上位3位以内の行が足りない。`--target-max-pos 5` に広げるか、期間を延ばす。広げた場合はその旨を報告に書く |
| 期待CTRが空欄の区間が多い | 期間を延ばす（季節性に注意）、`--min-bucket-rows` を下げる（精度は落ちる）、`--benchmark` に自サイトの過去の実績を渡す |
| ブランド名クエリが結果に残る | `--exclude-regex` に表記ゆれを追加して再実行する |
| 前年のデータがない | decay.py の `--previous` に直前の同じ長さの期間を渡し、季節性と需要減を区別できないことを報告に書く |

### 手順3 順位8〜20位のクエリに対応する

striking.csv を `impressions` の降順に並べ直し、上位30件について次の1〜5を確認する。スクリプトの並び順は `est_extra_clicks` の降順で、`--top` もその順で切るので、`--top` を付けずに出力してから並べ替える。結果はクエリごとに1行の打ち手にまとめ、表示回数の多い順に並べる（「5. 出力フォーマット」）。

1. どのページが表示されているか。CSV に `page` 列があればそれを使う。なければ Search Console の「検索パフォーマンス」→「+ フィルタを追加」→「クエリ」で対象クエリに絞り込み、表の「ページ」タブを見る。
2. それは正しいページか。同じクエリで複数のページが表示されている、または別のページのほうが検索意図に合う場合は、カニバリゼーションを疑う。統合するか、リライトで役割を分ける（鉄則7、[04-topical-map.md](04-topical-map.md)）。
3. そのページはクエリに答えているか。上位10件と検索意図・形式を比べ（[05-serp-brief.md](05-serp-brief.md)）、足りない節を挙げる。上位が比較・一覧なのに自ページが用語解説、のように形式が違う場合は、形式を合わせるか、別の既存ページに役割を移す。体験談・独自データが必要な箇所は `[要追加: ○○]` とする（鉄則5、[06-writing-editing.md](06-writing-editing.md)）。
4. クエリの主要な語句が title・H1・H2 に入っているか。入れるべきかは検索意図で判断し、入れる場合も文として自然に読めるようにする（[07-on-page.md](07-on-page.md)）。
5. このページに向けるべき内部リンク2本。同じトピックでクリックや被リンクの多いページから選ぶ（[08-internal-linking.md](08-internal-linking.md) の手順5）。

- 1行の打ち手には分類（手順7）を1つ付ける。同じページに複数のクエリが当たる場合は、打ち手を1回の変更にまとめ、反映日を1つにする。判定待ちのページには新しい打ち手を重ねない。
- 影響度は、`est_extra_clicks` の大きさとページの CV への近さで付ける。CV に関係しない情報クエリは、`est_extra_clicks` が大きくても影響度を下げる。

### 手順4 低CTRのページに対応する

1. 候補を抽出する。ページ別の CSV で、平均掲載順位5位以内なのに、同程度の順位のほかのページより CTR が明らかに低いページを探す（`low_ctr.py ページ.csv --max-pos 5`）。ブランド名で検索されるページ（トップページ、会社概要など）は `--exclude-regex` に URL の一部を入れて外す。除外しないと期待CTRが高く出て、ほかのページが過剰に抽出される。
2. 内訳を確かめる。ページ別の結果は候補の抽出までに使う。ページの行にはブランド名のクエリと非ブランドのクエリ、デバイス、検索での見え方が混ざっているので、平均掲載順位が同じでも、CTR の差を title のせいとは言えない。title・meta description を直す前に、「検索パフォーマンス」をそのページで絞り込み、次を見る（エクスポートの方法は「2. 必要な入力データ」）。
   - クエリ別: ブランド名を含むクエリと含まないクエリで、表示回数・CTR・平均掲載順位がどう分かれるか。
   - デバイス別と検索での見え方別: CTR の低さが特定のデバイスや表示のされ方に偏っていないか。
   - 非ブランドのクエリでも同程度の順位のわりに CTR が低いときに、title・meta description を直す対象にする。偏りがデバイスや見え方で説明できるなら、その要因を先に調べる。
   - 可能なら、サイト全体のクエリ別の CSV（手順2 の `クエリ.csv`）でも low_ctr.py を回し（ブランド名は `--exclude-regex` で除く。`--max-pos` の既定は 10）、抽出されたクエリが、そのページで絞り込んだクエリ別のファイルに入っているかを見る。ページで絞り込んだファイルに回すと、期待CTRがそのページのクエリだけで計算されるので使わない。API などのクエリ×ページの CSV なら、出力にページの列も残る。
3. SERP を確認する。AI による概要、強調スニペット、広告、動画・画像の枠、ショッピングの枠、他社のリッチリザルト（レビューの星、価格など）がないかを見る。Web 検索ツールで見た結果は「参考値」と書く。
   - SERP 機能が画面の上部を占めている場合、title の改善で取り戻せるクリックは小さい。影響度を下げる。
   - 実際に表示されている title が自ページの `<title>` と違う場合は、Google が書き換えている。title と H1・本文の整合を見直す（[07-on-page.md](07-on-page.md)）。
4. title と meta description を書き直す（[07-on-page.md](07-on-page.md)）。変更前と変更後を並べて示し、どちらにも文字数を併記する。検索意図に答える語句と、他の結果との違い（対象者、価格の有無、手順の数など事実に基づくもの）を入れる。更新していないのに年号だけを変えない。
5. 平均掲載順位は日によって変わる。`position` が 5 でも、2位の日と9位の日が混ざっていることがある。対象のページやクエリで絞り込み、「日付」タブの日別の推移を見てから判断する。

### 手順5 下落に対応する

decay.py の `diagnosis` で当たりを付け、下の「原因の候補と確かめ方」で原因を確かめてから打ち手を決める。

| diagnosis | 最初に確認すること | 打ち手 |
|---|---|---|
| 消失（今期のデータなし） | 下の「消失の確認」 | 技術的な原因を直す（[02-technical-audit.md](02-technical-audit.md)）。URL を変えたならリダイレクト先で実績を見る |
| 順位低下 | SERP の変化（新しい競合、上位ページの形式の変化、SERP 機能の追加）、上位ページとの内容の比較、同じ時期のアルゴリズム更新 | 検索意図に合わせて内容を更新する（[05-serp-brief.md](05-serp-brief.md)、[06-writing-editing.md](06-writing-editing.md)）、内部リンク（[08-internal-linking.md](08-internal-linking.md)） |
| 需要減（表示回数が減少・順位は維持） | 前年同期と比べたか（直前の期間と比べた結果なら季節性を疑う）、Google トレンドでの関心度の推移（過去5年。相対値なので推移の形だけを見る） | 季節性なら書き直さない。市場全体の需要が落ちているなら、新しいテーマの検討に回す（[04-topical-map.md](04-topical-map.md)） |
| CTR低下（順位・表示回数は維持） | SERP 機能や AI による概要の出現、競合のリッチリザルト、title の書き換え、生成 AI パフォーマンス レポートでの同じページの表示回数の推移 | title と meta description の見直し（[07-on-page.md](07-on-page.md)） |
| 複合要因 | 日別の推移、デバイス別・国別、そのページで絞り込んだうえでのクエリ別に分解する | 分解した結果ごとに上の行の手順に戻る |

消失の確認（上から順に）:

1. 今期の CSV がちょうど1,000行なら、上位1,000行から外れただけではないかを、Search Console でその URL に絞り込んで確かめる。クエリの CSV で比べた場合は、匿名化で表に出なくなっただけのこともあるので、表示されていたページのページ別の数値で確かめる（手順1）。
2. 標準エラーに URL の表記の違い（パスの大文字・小文字、末尾の `/`）の注意が出ていれば、URL の変更とリダイレクトの有無を確かめる。
3. URL 検査でインデックスの状態を見る。
4. audit.py の `status`（404・301）、`canonical`、`robots_noindex` と robots.txt を見る。

原因の候補と確かめ方:

| 原因の候補 | 確かめ方 |
|---|---|
| 情報が古い | ページの最終更新日と、上位ページが扱っている新しい情報（制度・価格・仕様の変更など）を比べる |
| 強い競合の出現 | 対象クエリの SERP で、自ページより上に新しく入ったページ・サイトがないか。記録があれば前年と比べる |
| 検索意図の変化 | 上位ページの形式（一覧・比較・解説・商品ページなど）が自ページと違っていないか |
| カニバリゼーション | そのクエリで自サイトの複数のページが表示されていないか（クエリで絞り込み →「ページ」タブ）。新しく公開した自サイトのページに流入が移っていないか |
| AI による概要がその質問に答えるようになった | SERP で AI による概要が出ているか（目視）。順位と表示回数が保たれたまま CTR が落ちていないか。自サイトが AI による概要・AI モードでリンクされているかは、生成 AI パフォーマンス レポートのページ別の表示回数で見る |

- アルゴリズム更新の時期は Google 検索ステータス ダッシュボード（status.search.google.com）で確認する。コアアップデートの場合、Google は完了から少なくとも1週間待ってから、ロールアウト開始前の1週間と比べるよう案内している。
- 小さな順位の変動は常に起きる。Google のドキュメントも、すでに成果が出ているページに大きな変更を加えないよう勧めている。`pos_diff` が小さい行は経過観察にする。

### 手順6 施策表にまとめる

- 見つかった候補を SKILL.md の施策表にまとめる。影響度は CV への近さ（GA4 のキーイベント）と、`est_extra_clicks`・`lost_clicks`・`clicks_diff` の大きさで付ける。工数と優先度の付け方、ほかの施策の前提になる施策（消失の技術的な原因の修正など）の並べ方は [00-principles.md](00-principles.md)（優先度 = 影響度 ÷ 工数、鉄則3）。
- 根拠データの列には、使ったファイル名・期間・スクリプトの引数を書く。
- 判定待ちのページは施策表に載せても実施を判定日の後に回す。改善対象が見つからなければ、施策表を作らず「今回はなし」と報告する。

### 手順7 効果を測る

- 観察の起点は、編集日ではなく本番への反映日（以下 D）。変更ごとに、反映日・URL・対象クエリ・分類・変更内容・変更前の値を変更ログに記録する。
- 観察日数は28日を基本にする。Google のクロールには数日から数週間かかることがあり（[クロール・インデックス登録リクエスト](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl?hl=ja)）、4週間なら曜日の構成もそろう。7日は、表示回数が十分に多いページで変化の兆しを早く見る場合に限る。反映前の連続する2つの7日間（D−14〜D−8 と D−7〜D−1）でクリック数や CTR が大きく違うページは、7日では見ない。
- 判定日は「反映日 + 観察日数 + 遅延日数」以降にする。遅延はデータの反映の遅れで、目安は3日（通常2〜3日。公式の「データの鮮度」の説明を確認し、断定しすぎない）。
  - 例: 28日間を観察するなら、D の31日後に判定する。窓は D+1〜D+28、比較対象は反映前の同じ長さ・同じ曜日構成の期間（D−28〜D−1）。
  - 7日で見る場合（上の条件を満たすページだけ）は D の10日後に判定し、窓は D+1〜D+7、比較は D−7〜D−1。
  - 反映の直後に「直近28日」「直近7日」を見ると、窓の一部が反映前のデータになる。窓は反映後の期間に丸ごと収める。
- 対照を並べる。同じカテゴリ（できれば同じテンプレート）で観察期間中に変更していないページを選び、同じ2つの期間の増減を対象と並べる（1ページより複数ページの合計のほうが揺れが小さい）。季節性・アルゴリズムの更新・SERP の変化によるサイト全体の変動は対照にも出るので、対象の変化から対照の変化を差し引いて読む。季節性がある場合は、前年同期の同じ期間の変化率とも比べる。
- 判定は次の4つのどれかにする。対照との差がどれだけあれば改善・悪化とみなすかは、反映前に決めて変更ログに書く。
  - 改善 / 悪化: 対象の指標が、対照の変化を超えて良くなった / 悪くなった。
  - 変化なし: 観察の条件を満たしたうえで、対照と比べて差がない。
  - 判定不能: 表示回数が少なく偶然の揺れと区別できない、期間中にコアアップデートなどの大きな変動が重なった（影響がページごとに違うので対照では差し引ききれない）、判定日に URL 検査で見た最終クロール日が反映日より前（Google がまだ変更を見ていない）、など。観察日数を延ばすか、再クロールや変動の後に同じ規則で窓を取り直す。判定日も同じだけ後ろにずれる。
- 判定日までは、同じページ・同じクエリ群に別の変更を入れない（効果を切り分けられなくなる）。1つのページに入れる変更は、1回の判定につき1つの分類にする。複数の分類を同時に入れた場合は、主な分類を1つ付け、どれが効いたかは切り分けられないと記録する。
- 分類は次から1つ選ぶ。必要なら分類を足してよい。
  - `meta-rewrite`: title・meta description の書き換え
  - `content-gap`: 不足している論点の追加
  - `internal-link`: 内部リンクの追加・変更
  - `real-data`: 一次データ・事例の追加
  - `structure`: 見出し構成・ページ構造の変更
- 判定が「変化なし」「悪化」だったページ・クエリへの次の打ち手は、前回と別の分類から選ぶ。同じ手を繰り返さない。この規則は、観察の条件を満たして「変化なし」「悪化」と判定できた場合に限る。「判定不能」は失敗ではないので、分類を変えずに観察を延ばす。
- 報告するのは「何を変えたか」と判定予定日まで。効果は予測で断定せず、判定日の実測で決める。
- クエリ単位の比較では匿名化されたクエリが抜ける。ページ単位の数値でも確認する。
- Search Console のアノテーション（グラフを右クリックして追加、1件120字まで、1プロパティ200件まで）は補助に使える。500日を過ぎると自動で削除され、編集もできない。プロパティのユーザー全員が見られる（追加・削除は所有者とフル権限のユーザーだけ）ので、機密情報を書かない。長期の記録は自社の変更ログに残す。

## 6. よくある失敗

- 比較表示のままエクスポートする: 列名に期間ラベルが付き、decay.py が読めない。期間ごとに1回ずつエクスポートする。
- 反映直後の「直近28日」「直近7日」や、長さ・曜日構成の違う期間で判定する: 窓の一部が反映前のデータになり、曜日の違いだけでも増減が出る。反映日の翌日から窓を取り、反映前の同じ長さ・同じ曜日構成の期間と比べる。
- 判定前の同じページに別の変更を重ねる: どの変更が効いたか判定できない。判定日（反映日 + 観察日数 + 3日）までは同じページ・同じクエリ群に手を入れない。
- 効果がなかった打ち手と同じ分類を繰り返す: 変化なし・悪化と判定できたら、次は別の分類（例: meta-rewrite の次は content-gap）を選ぶ。判定不能は効果がなかったことにならないので、分類を変えずに観察を延ばす。
- ブランド名クエリを除外しない: 期待CTRと目標CTRが高く出て、一般クエリが過剰に抽出される。表記ゆれを含めて除外する。
- ページ別の low_ctr.py の結果だけで title を書き換える: ページの行にはブランド名のクエリ・デバイス・検索での見え方が混ざる。そのページで絞り込み、クエリ別とデバイス別の内訳を見てから直す。
- 数百万行の一括エクスポートをそのままスクリプトに渡す: ファイル全体をメモリに読み込むので、先に期間とキーごとに集計する。掲載順位は最上位を 0 とした値で入っているので、手順1の式で出す。
- est_extra_clicks を予測として報告する: 自サイトの実績 CTR を当てはめた目安にすぎない。候補の並べ替えだけに使う。
- 前期比だけで下落を判断し、季節的な需要減で記事を書き直す: 直近3か月と前年同期の3か月を比べ、季節性なら書き直さない。
- クエリ別データで表示回数が0、または行がないことを「表示されていない」「インデックスされていない」と読む: 匿名化されたクエリは表に出ず、画面の「~」「-」はファイルでは 0 になる。インデックスの有無は URL 検査かページ インデックス登録レポートで確かめ、サイト全体の増減はグラフの合計かページ別のデータで見る。
- 標準出力をリダイレクトしたファイルを Excel で開く: 標準出力は BOM なしなので文字化けすることがある。Excel で開くなら `-o` を使う。`-o` のファイルを機械で処理するときは先頭の `'` を除くか `--no-sanitize` で出し直す。
- 対照を置かずに判定する、判定不能を「変化なし」として扱う: サイト全体の変動を施策の効果と取り違える。同じカテゴリの変更していないページと並べ、表示回数が少ない場合や大きな変動と重なった場合は判定不能として観察を延ばす。
