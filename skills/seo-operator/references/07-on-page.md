# 07 オンページ要素

title・meta description・見出し・画像・URL・OGP・構造化データをページごとに点検し、改善案を文字数付きで出すためのファイル。

## 1. 目的

- 検索結果での見え方（タイトルリンクとスニペット）を、ページの内容と検索意図に合わせて整え、クリックされる理由を作る。
- ページの主題を title・h1・本文冒頭・構造化データで一貫させ、案は担当者がそのまま CMS に入力できる形（全角換算の文字数付き、JSON-LD はコピーして使える形）で出す。
- 対象外: 本文の書き直しは [06-writing-editing.md](06-writing-editing.md)、狙うクエリの選定は [03-keyword-research.md](03-keyword-research.md) と [10-gsc-growth.md](10-gsc-growth.md)、AI 検索向けの調整は [09-ai-search.md](09-ai-search.md)、インデックスの問題は [02-technical-audit.md](02-technical-audit.md)。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|
| 現在の title・meta description・h1 | `scripts/audit.py` の出力（audit.csv）。または Screaming Frog の Internal タブ（HTML）→ Export | 必須 | 対象 URL と現在の title・description を貼ってもらう |
| ページごとの検索クエリ | Search Console →「検索パフォーマンス」→「検索結果」→ フィルタでページの URL を指定 →「クエリ」タブ →「エクスポート」 | 必須 | ページの内容から主題を読み取って案を作り、「クエリ未確認」と明記する（`[要追加: GSCのクエリ別データ]`） |
| CTR が低いクエリ・ページ | `scripts/low_ctr.py` の出力（[10-gsc-growth.md](10-gsc-growth.md)） | 任意 | audit.csv の title なし・重複から着手する |
| ブランド名の表記・CV・表記ルール | `seo/site-brief.md`、`seo/voice-guide.md` | 必須 | ブランド名の位置に `[要追加: ブランド表記]` を残す |
| 上位ページの title | [05-serp-brief.md](05-serp-brief.md) の SERP 分析、またはシークレットウィンドウで検索した上位10件を貼ってもらう | 任意 | 自サイトの情報だけで案を作り、競合の傾向には触れない |
| 既存の構造化データ | リッチリザルト テスト、Search Console の URL 検査 | 任意 | テンプレートごとに代表 URL を1件ずつテストしてもらう |
| 構造化データに入れる事実（価格・在庫・住所・営業時間・著者） | 商品データベース、店舗情報、CMS の著者情報 | 構造化データを作る場合は必須 | 値を推測で埋めない。わからないプロパティは JSON-LD に書かず、JSON-LD の外に「未記入のプロパティ: [要追加: ○○]」として列挙する（鉄則1・5） |

## 3. 手順

1. 対象ページを決める。CV ページで title がない・重複しているもの → `low_ctr.py` で CTR が低いページ → 順位8〜20位のクエリを持つページ、の順に見る。表示回数がほぼないページは title を変えても効果を確かめられないので、先に [02-technical-audit.md](02-technical-audit.md) でインデックスの状態を確認する。
2. ページの主題とクエリを確かめる。GSC のクエリ別データで、表示回数の多いクエリと検索意図を確認する。同じクエリで自サイトの複数ページが表示されていれば、title を直す前に統合かリライトを検討する（鉄則7、[04-topical-map.md](04-topical-map.md)）。
3. title を作る。
   - 目安は全角換算30字前後。Google は title の長さに上限を設けておらず、表示はデバイスの幅に合わせて切り詰められる（文字数ではなくピクセル幅で決まる）。半角英数字は全角の約半分の幅なので、全角換算で数える。
   - 後半が切れても意味が通るように、主なクエリの語とページで得られるものを前半に置く。
   - クリックする具体的な理由を1つ入れる: 数字（比較の観点の数、手順の数）、年、得られる結果、形式（比較表、テンプレート、チェックリストなど）。年は毎年内容を更新する運用がある場合だけ入れる。ページにない内容や誇張で釣らない。
   - ブランド名は末尾に区切り記号（`｜` や `-`）で付ける。Google もサイト名は先頭か末尾に区切り記号で分けて置くよう勧めている。ブランド名が検索結果のサイト名と重複すると、Google がタイトルリンクから省くことがある。
   - サイト内で一意にする。テンプレートが同じ title を量産していれば、テンプレートの修正を1つの施策にする。
   - h1 は title とほぼ同じ文言にする（手順6）。Google は title のほか、ページの主な見出し、h1 などの見出し、og:title、目立つテキスト、ページ内外のアンカーテキスト、WebSite 構造化データからタイトルリンクを自動生成するので、ページ内容と一致しているほど書き換えられにくい。
   - Google が書き換えやすい title を避ける: 一部が空の title、更新されていない年や日付、内容と合わない title、複数ページで同じ定型文、同じ大きさの見出しが並んでメインのタイトルがわからないページ、本文と言語や文字体系が違う title。
   - キーワードの繰り返しや羅列はしない。title の変更は、Google が再クロールして処理するまで反映されない（数日〜数週間）。
   - 案は5つ出し、それぞれに全角換算の文字数と、入れたクリックの理由（数字・年・結果・形式）を添える。第1案を推奨とし、理由を書く。
4. meta description を作る。
   - 目安は全角換算80〜120字前後。長さの上限はなく、表示は必要に応じて切り詰められる。
   - 順位を上げる要素ではない（Google は 2009 年に meta description をランキングに使っていないと説明している）。検索結果に使われたときのクリックに影響する。Google はスニペットを主に本文から作り、meta description のほうがページを正確に説明できる場合に使うので、表示されない場合もある前提で書く。
   - ページごとに固有にし、そのページでわかること・対象者・具体的な情報（価格帯、対応地域、手順の数など）を入れる。主なクエリの語は自然に入れ、並べない。キーワードを並べただけの説明文は使われにくい。EC の商品ページのように数が多い場合は、商品データから文を組み立てる方法でもよい。
   - ページで得られるものを約束し、ページにない内容は約束しない（釣りをしない）。
   - 案は3つ出し、それぞれに全角換算の文字数を添える。
5. 文字数を数えて案に併記する。数え方は下の「全角換算の数え方」に従い、案を出すたびに `（全角換算 29字）` の形で書く（SKILL.md の出力の共通ルール）。audit.csv の値を使うときの注意:
   - title_len と desc_len は Python の `len()` の文字数で、全角換算とは違う。
   - title・desc が Excel の1セルの上限（32,767 文字）を超えるページは、セルには先頭だけが入り、title_len・desc_len は元の文字数を示す。テンプレートの不具合を疑う。
   - title・desc の先頭が `=` `+` `-` `@` のセルには、CSV インジェクション対策で `'` が付いている（`--no-sanitize` で取り直せば付かない）。文字数を数えるときは除く。title_len・desc_len は `'` を含まない元の文字数。
   - title は HTML の仕様どおり、`<title>` の中のタグも文字列として入る（例 `foo <b>bar</b>`）。
6. 見出しを整える。
   - h1 はページに1つ、主題を表し、title とほぼ一致させる（ブランド名と区切り記号を除いた部分をそろえる。完全に同じでなくてよい）。Google は見出しの数や順序に理想はないとしているが、読み手（スクリーン リーダーを含む）とテンプレート管理のために1つにそろえる。
   - h2 は、見出しだけを読めば検索者が知りたいことの目次になるように並べる。副キーワードは自然に入る場合だけ h2 に入れる。h3 は内容の階層どおりに使う。文字の大きさを変える目的で見出しタグを使わない。
   - 見出しにキーワードを詰め込まない。同じ語を全部の h2 に入れる必要はない。
7. 本文冒頭で答える。h1 の直後の段落で、主なクエリへの答え（結論）を、2〜3文・100〜150字程度の、単独で引用できる完結した文で書き、その後に根拠と詳細を続ける（鉄則4と同じ考え方）。長い前置きや「この記事では〜を紹介します」だけの導入は削る。
8. 画像を点検する。
   - alt は画像の内容を文脈に沿って説明する。装飾だけの画像は `alt=""`。alt にキーワードを並べない。ファイル名は内容がわかる英小文字とハイフンにする（例 `keihi-seisan-flow.png`）。
   - `width` と `height` 属性（または CSS の `aspect-ratio`）で表示領域を確保し、レイアウトのずれ（CLS）を防ぐ。ファーストビューの主画像には `loading="lazy"` を付けない（LCP が遅れる）。
   - Google 検索が対応する形式は BMP、GIF、JPEG、PNG、WebP、SVG、AVIF。写真は WebP や AVIF で容量を下げ、`srcset` や `<picture>` で画面幅に合う大きさを出し分ける。
   - 検索で見つけてほしい画像は `<img>` の `src` で置く。CSS の背景画像は Google がインデックスしない。
9. URL を点検する。
   - 短く、内容がわかる単語をハイフンでつなぐ（アンダースコアより推奨されている）。大文字と小文字は別の URL として扱われるので、小文字にそろえる。
   - 日本語 URL は使えるが、リンクやサイトマップではパーセントエンコード（UTF-8）した形で書く。共有時に長い文字列になる、表記ゆれで別 URL ができやすい、という欠点を踏まえて新規ページの方針を決める。
   - URL の中のキーワードは順位への効果が小さい（Google の SEO スターター ガイド）。既存 URL をキーワードのために変えない。変える場合は 301 リダイレクト、内部リンク、サイトマップ、canonical をまとめて直す。
10. OGP を点検する。OGP は SNS やチャットで URL が共有されたときの表示を決めるもので、順位対策として設定するものではない。ただし Google は og:title をタイトルリンクの情報源の1つに、og:site_name をサイト名の情報源の1つに挙げているので、title・サイト名と矛盾させない。`og:url` は canonical と同じ URL にする。
    ```html
    <meta property="og:title" content="経費精算システムの選び方と比較の5観点">
    <meta property="og:description" content="{ページの説明}">
    <meta property="og:image" content="https://example.jp/images/ogp/keihi-seisan.png">
    <meta property="og:url" content="https://example.jp/column/keihi-seisan">
    <meta property="og:type" content="article">
    <meta property="og:site_name" content="サンプル社">
    <meta name="twitter:card" content="summary_large_image">
    ```
11. 構造化データを選んで書く。
    - 構造化データはそれだけで順位を上げない。ページの内容を検索エンジンに伝え、リッチリザルトの対象になるためのもの。
    - 形式は JSON-LD を使う（Google が推奨）。`<script type="application/ld+json">` に入れ、`<head>` と `<body>` のどちらに置いてもよい。
    - 下の「ページの種類と構造化データ」で型を選び、「JSON-LD の最小例」をもとに、与えられた実情報で埋められるプロパティだけを書く。日付（`datePublished`・`dateModified`）は ISO 8601 形式で実際の公開日・更新日を書く。
    - 値がわからないプロパティは JSON-LD から削り、`[要追加: ○○]` などのプレースホルダーを JSON-LD の値に入れない（差し替え漏れのまま公開されると、誤った値を検索エンジンに渡す）。削ったプロパティと、埋めるのに必要なデータ（入手元）は、JSON-LD の外に「未記入のプロパティ: [要追加: ○○]」として列挙する（鉄則1・5）。必須のプロパティ（下の表）が埋まらない型は、データがそろうまで入れない。
    - ページに表示していない情報をマークアップしない。構造化データのあるページを robots.txt や noindex でブロックしない。正しく書いてもリッチリザルトの表示は保証されないので、提供終了した型に工数をかけない（下の「リッチリザルトの提供状況」）。
    - レビュー: 評価対象の事業者が自分についてのレビューを管理している場合、`LocalBusiness` や `Organization`（サブタイプを含む）のページは星評価の対象外になる（self-serving reviews）。偽のレビューや、見返り（金銭・割引・無料の商品など）を受けたことを明示していないレビューは、ページにも構造化データにも載せない（2026年7月にガイドラインへ追加）。日本では、事業者が関与したことを表示しないレビューは景品表示法のステルスマーケティング規制（2023年10月施行）に触れるおそれがある（[06-writing-editing.md](06-writing-editing.md)、[11-link-building.md](11-link-building.md)）。
12. 検証して反映を確かめる。
    - 公開前にリッチリザルト テストで、Google のリッチリザルトの対象になるかを確認する。schema.org の構造に合っているかだけを確かめたいとき（対象外の型を含む）は Schema Markup Validator を使う。公開後は Search Console の「拡張機能」（商品は「ショッピング」）のレポートと URL 検査で確認する。
    - title・description の効果は、本番への反映日を起点に実測で判定する（[10-gsc-growth.md](10-gsc-growth.md) の「手順7 効果を測る」）。判定日は反映日 + 観察日数 + データの遅延日数。観察日数は28日が基本で、遅延3日なら反映日の31日後に判定し、窓は反映日の翌日から28日間（D+1〜D+28）。7日で見るのは、表示回数が十分に多いページで変化の兆しを早く見る場合だけ。比較対象は反映前の同じ長さ・同じ曜日構成の期間の CTR とクリック数で、同じカテゴリの変更していないページ（対照）の同じ2つの期間の増減も並べる。判定日までは同じページ・同じクエリ群に別の変更を入れない。変更ログの分類は `meta-rewrite`（見出しの変更は `structure`）。
    - 判定は改善・変化なし・悪化・判定不能の4つ。効果を予測で断定しない。表示回数が少ない、コアアップデートなどの大きな変動が重なった、最終クロール日が反映日より前、のどれかなら判定不能とし、分類を変えずに観察を延ばす。「変化なし」「悪化」と判定できた場合だけ、次は別の分類の打ち手（`content-gap`・`internal-link` など）を選ぶ。

### 全角換算の数え方

- 定義: 全角文字（漢字・ひらがな・カタカナ・全角記号）を 1、半角英数字・半角記号・半角スペース・半角カナを 0.5 として合計し、端数は切り上げて整数で書く（29.5 → 30字）。
- 判定は `unicodedata.east_asian_width` の値で行い、`F`・`W`・`A` を 1、それ以外（`Na`・`H`・`N`）を 0.5 とする。`A`（①、○、… など）は日本語フォントでは全角幅で表示されるため 1 とする。
- 例（架空）: `SEO対策の基本とGoogle Search Consoleの使い方` は `len()` では 34字、全角換算では 22字。

1件だけ数える:

```bash
python3 -c 'import sys,math,unicodedata as u; print(math.ceil(sum(1 if u.east_asian_width(c) in "FWA" else 0.5 for c in sys.argv[1])))' "経費精算システムの選び方と比較の5観点｜サンプル社"
```

複数の案をまとめて数える（1行1案）:

```bash
python3 -c 'import sys,math,unicodedata as u; [print(math.ceil(sum(1 if u.east_asian_width(c) in "FWA" else 0.5 for c in s)), s, sep="\t") for s in sys.stdin.read().splitlines() if s.strip()]' < titles.txt
```

例（架空）:

| 種類 | 案 | 全角換算 | 判断 |
|---|---|---|---|
| title | 経費精算システムの選び方と比較の5観点｜サンプル社 | 25字 | 主なクエリの語が先頭、ブランド名は末尾 |
| title（避ける） | サンプル社｜経費精算システムの選び方と比較の5観点 | 25字 | ブランド名が先頭で、切れたときに主題が残りにくい |
| meta description | 経費精算システムを初めて導入する中小企業向けに、比較するときの5つの観点（費用、会計ソフト連携、承認フロー、スマホ対応、サポート）と導入までの手順をまとめました。 | 81字 | 対象者・わかること・具体的な観点が入っている |

### ページの種類と構造化データ

| ページの種類 | 入れる型 | 備考 |
|---|---|---|
| トップページ | `Organization`、`WebSite` | Organization はトップか会社概要の1ページに置く。必須プロパティはない。サイト名を指定したい場合は WebSite の `name` と `url` をトップに置く |
| 記事 | `BlogPosting` / `NewsArticle` / `Article`、`BreadcrumbList` | 必須プロパティはない。`headline`・`image`・`datePublished`・`dateModified`・`author` を入れる。著者は `Person`、法人名義は `Organization` |
| 購入できる商品ページ | `Product` + `Offer`（販売者のリスティング）、`BreadcrumbList` | 必須は `name`・`image`・`offers`（`price` と `priceCurrency`）。価格と在庫はページの表示と一致させる。返品・送料のポリシーは `Organization` 側にまとめて書ける |
| 購入できない商品レビュー・比較記事 | `Product`（商品スニペット）+ `Review` | 他サイトへのリンクで販売しているページは販売者のリスティングの対象外 |
| 店舗・拠点ページ | `LocalBusiness` の具体的なサブタイプ（`Restaurant` など） | 必須は `name` と `address`。営業時間・電話番号は店頭の表示と一致させる |
| カテゴリ・一覧 | `BreadcrumbList` | パンくずは 2025年1月からモバイルの検索結果に表示されない（パソコンでは表示される）。マークアップはそのままでよい |
| よくある質問 | 不要 | FAQ のリッチリザルトは提供終了。AI 検索対策としても勧めない。Q&A の本文は読み手のために残してよい |
| 手順の解説 | 不要 | HowTo のリッチリザルトは廃止済み |

### JSON-LD の最小例

値はすべて架空。実データに置き換え、わからない値はプロパティごと削る（JSON-LD の中にプレースホルダーを書かない）。削ったプロパティは JSON-LD の外に列挙する（例: `未記入のプロパティ: [要追加: sku（商品データベースの品番）]`）。

Organization（トップページ）:

```json
{
  "@context": "https://schema.org",
  "@type": "Organization",
  "name": "サンプル株式会社",
  "url": "https://example.jp/",
  "logo": "https://example.jp/images/logo.png",
  "sameAs": ["https://www.example.com/profile/sample-inc"]
}
```

BlogPosting（記事。報道記事なら `NewsArticle`）:

```json
{
  "@context": "https://schema.org",
  "@type": "BlogPosting",
  "headline": "経費精算システムの選び方と比較の5観点",
  "image": ["https://example.jp/images/keihi-16x9.jpg", "https://example.jp/images/keihi-4x3.jpg", "https://example.jp/images/keihi-1x1.jpg"],
  "datePublished": "2026-04-01T09:00:00+09:00",
  "dateModified": "2026-06-15T10:30:00+09:00",
  "author": [{"@type": "Person", "name": "山田 太郎", "url": "https://example.jp/authors/yamada"}]
}
```

BreadcrumbList（最後の項目は `item` を省略でき、その場合はページ自身の URL が使われる）:

## 6. よくある失敗

- `len()` や文字数カウンターの値をそのまま全角換算として書く: 半角英数字が多い title で文字数を多く見積もる。「全角換算の数え方」で数え直してから併記する。
- 全ページの title の先頭にブランド名を置く: 切り詰められたときに主題が残らない。ブランド名は末尾に区切り記号で付ける。
- title と h1 の主題がずれている: Google が h1 などからタイトルリンクを作り直すことがある。検索意図を一つに決めて両方をそろえる。
- 年号や数字を内容と合わないまま入れる: 更新しない「2025年版」や、本文にない「10選」は書き換えの原因になり、クリックした読者を裏切る。年号は内容を毎年更新する場合だけ、数字は本文と一致する場合だけ入れる。
- meta description にキーワードを並べる、全ページで同じ文にする: スニペットに使われにくい。ページ固有の具体的な情報を書く。
- FAQPage を入れればリッチリザルトが出ると考える: FAQ のリッチリザルトは 2026年5月7日以降、Google 検索に表示されない。AI 検索対策にもならない。工数は本文の改善に回す。
- ページに表示していない情報を構造化データに入れる: ガイドライン違反で、リッチリザルトの対象外になる。表示中の内容だけをマークアップする。
- 自社が集めた自社のレビューで Organization や LocalBusiness に星を出そうとする: self-serving reviews として対象外。見返りを明示していないレビューはマークアップせず、景品表示法の観点でも確認する。
- 価格・在庫・営業時間を推測で埋める、ページの表示と食い違う: 実データから差し込む仕組みにし、わからない値はプロパティごと削る。
- JSON-LD の値に `[要追加: ○○]` を書く: 差し替え漏れのまま公開されると、プレースホルダーの文字列が商品名や著者名として検索エンジンに渡る。削ったプロパティは JSON-LD の外に「未記入のプロパティ: [要追加: ○○]」として列挙する。
- キーワードを入れるために既存の URL を変える: URL の中のキーワードは効果が小さく、リダイレクトと内部リンク修正の工数が増える。変えるなら 301・内部リンク・サイトマップ・canonical をまとめて直す。
