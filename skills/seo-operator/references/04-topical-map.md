# 04 トピカルマップ（クラスター設計）

[03-keyword-research.md](03-keyword-research.md) のキーワード一覧を「1つの検索意図 = 1つのURL」のクラスターにまとめ、既存ページとの対応、サイト構造、各クラスターの扱い（新規・リライト・統合・noindex・削除）、最初の20ページの公開順を決めるための手順。

## 1. 目的

- どのキーワードをどの URL で狙うかを一意に決める。同じ検索意図のページを複数作らない（鉄則7）。
- ピラー（ハブ）とクラスターの関係を、カテゴリ・URL 階層・パンくずリスト・内部リンクに落とし込む。
- 既存ページを棚卸しし、カニバリゼーション（同じクエリで自サイトの複数 URL が競合する状態）を見つけて解消方針を決める。
- クラスターごとに優先度（影響度 ÷ 工数、鉄則3）を付け、[05-serp-brief.md](05-serp-brief.md) と [08-internal-linking.md](08-internal-linking.md) に渡す。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|
| キーワード一覧（表記ゆれ、検索意図、ファネル、CV への近さ、リストA / B / C 付き） | 03 の出力 | 必須 | 03 を先に行う。候補リストしかない場合は、ボリューム・CV への近さを `[要追加: ○○]` にして構造だけ作る |
| 各キーワードの上位10件の URL | ユーザーが Google をシークレットウィンドウで検索し、上位10件の URL を貼る。または Ahrefs → Keywords Explorer → SERP overview のエクスポート、Semrush → Keyword Overview → SERP Analysis のエクスポート | 必須（まとめるかの判断に使う） | 重なりを確認できない組は、意図とページの種類だけで仮にまとめ、判断列に「仮（SERP 未確認）」と書く |
| 既存ページの一覧と状態 | `scripts/audit.py` の出力 CSV（url, status, title, h1_count, canonical, robots_noindex）、またはサイトマップ | 既存サイトは必須 | サイトマップの URL 一覧だけで棚卸しし、状態の列は `[要追加: audit.py の出力]` にする |
| クエリ × ページの実績 | Search Console API（`searchanalytics.query`、dimensions に `query` と `page`）、Data Studio（旧 Looker Studio）の Search Console コネクタで「URL のインプレッション」表、または Search Console の UI でクエリごとに絞り込み | 既存サイトは必須 | 主要なクエリだけ UI で1件ずつ確認する（「カニバリゼーションの確認手順」の1）。確認していないクラスターは「カニバリ未確認」と書く |
| ランディングページ別の CV | GA4 →「レポート」→「エンゲージメント」→「ランディング ページ」→ キーイベント数を表示 →「このレポートを共有」→「ファイルをダウンロード」→ CSV | 任意 | 統合先の選定を、クリック数・被リンク・内容で行い、根拠データ列に「CV 未確認」と書く |
| 被リンクのあるページ | Search Console →「リンク」→ 画面上部の「エクスポート」（外部リンク: 最新のリンク／その他のサンプルリンク）、または Ahrefs / Semrush の被リンク一覧のエクスポート | 任意（統合・削除の判断では必須） | 統合・削除の判断を「保留」にし、データを依頼する |

## 3. 手順

1. 検索意図で仮のグループを作る。
   - 03 の検索意図（仮）と語の意味で、同じ問いに答えるキーワードを同じグループに入れる。
   - 1グループに入れる基準は「1ページの中で、読者が途中で離れずに答えまでたどり着けるか」。答えるべき問いが2つに割れるなら分ける。

2. SERP の重なりで、まとめるか分けるかを決める（鉄則7）。判断ルールは下の「まとめる・分けるの判断ルール」に従う。
   - 比べるのは URL 単位。ドメイン単位で比べると、大手サイトや Q&A サイトがどの語にも出るジャンルで重なりを多く見積もってしまう。
   - SERP は同じ日・同じ条件（国、デバイス、シークレットウィンドウ）で集める。
   - Google の検索結果を独自スクリプトで自動取得しない。Google のスパムポリシーは、順位確認を目的としたスクレイピングを含む自動クエリの送信を「機械生成トラフィック」として禁止している。

3. ピラーとクラスターを設計する。
   - ピラーは、幅の広いテーマ（意図が広く、複数のクラスターを束ねる語）の入口になるページ。各クラスターの要点と、そのクラスターへのリンクを置く。
   - クラスターは、1つの具体的な意図に答えるページ。ピラーへリンクを返し、関連の強いクラスター同士だけを相互にリンクする。
   - ピラーにクラスターの本文を書き込まない。ピラーとクラスターが同じ意図を奪い合い、カニバリゼーションの原因になる。
   - ピラーを新しく作るのは、束ねるクラスターが複数あり、ピラー自体に対応する検索意図（「{テーマ}」「{テーマ} とは」「{テーマ} 種類」など）があるときに限る。束ねるだけで独自の内容がないページは作らない。
   - ピラーは最大6本にする。それより多くなるなら、事業に近いテーマに絞るか、クラスターに降ろす。各クラスターがつながるピラーは1つにする。
   - 各ページに、仮タイトル、主キーワード、同じページで扱う副キーワード（3〜8個）、検索意図、つながるピラーを決める。副キーワードが8個を超えるなら、意図が2つ混ざっていないかを手順2の基準で見直す。

4. カテゴリ・URL 階層・パンくずリストに対応させる。
   - ピラー = カテゴリ（または親階層）、クラスター = その下の子ページ、を基本にする。例: `/{pillar-slug}/` と `/{pillar-slug}/{cluster-slug}/`。
   - URL は内容が推測できる語で作る。日本語の単語を URL に使ってよいが、リンクの href ではパーセントエンコードする（Google の URL 構造のガイドライン）。英字スラッグにするか日本語にするかは、サイト内で統一する。
   - 階層は、カテゴリの数と量が必要とする分だけにする。見た目の整理のためだけに階層を足さない。
   - 既存 URL の変更は、301 リダイレクトと内部リンクの張り替えが必要になる。構造をきれいにするためだけに既存 URL を変えない。変えるなら理由と影響を施策表に書く。
   - パンくずリストはページ上の表示と BreadcrumbList の構造化データをそろえる。Google の検索結果でパンくずリストが表示されるのは、2025年1月以降パソコン版のみ。サイト内の回遊と階層の明示のために設計する。

5. 既存ページを棚卸しし、各クラスターに担当 URL を1つ割り当てる。
   - 既存 URL ごとに、主なクエリ（GSC）、クリック数・表示回数、CV（GA4）、被リンク、状態（`scripts/audit.py` の status / canonical / robots_noindex）を並べる。audit.csv では、HTML でない 2xx の行（PDF など）にも HTTP ヘッダーから canonical・canonical_mismatch・robots_noindex が記録され、title・desc・h1_count・word_count などは空欄になる。HTML のページだけを並べるときは、h1_count が空欄でない行に絞る。status が `BLOCKED:` / `SKIPPED:` で始まる行は取得していないので、件数を別に数え、[02-technical-audit.md](02-technical-audit.md) の「audit.csv の判断ルール」で扱う。`SKIPPED:other-host` が多ければ、サイトマップのホストを直してから取り直すか、`--allow-other-hosts` を付けて取り直す。
   - audit.csv の文字列の列（url, redirect_to, title, desc, canonical）は、先頭が `=` `+` `-` `@`（またはタブ・CR）のセルに `'` が付いている（CSV インジェクション対策）。title を比べるときは先頭の `'` を除くか、`--no-sanitize` を付けて出し直す。
   - 1つのクラスターに担当候補が2つ以上あれば、手順6のカニバリゼーションの確認と、下の「判断の分岐」で1つに決める。
   - 担当できる既存ページがない場合だけ「新規」にする。

6. カニバリゼーションを確認する。手順は下の「カニバリゼーションの確認手順」に従う。

7. 優先度を付ける（鉄則3）。
   - 影響度（1-5）と工数（1-5）は [00-principles.md](00-principles.md) の採点基準で付け、優先度 = 影響度 ÷ 工数（小数第1位まで）。同じ値なら影響度が高いほうを先にする。
   - 影響度の材料は、03 の CV への近さと、クラスター全体の流入の規模（基準ツールのボリューム、既存ページの表示回数）。データがなければ影響度を「暫定」と明記する。
   - 統合・リダイレクトのように開発や CMS 設定が必要な施策は、工数を低く見積もらない。

8. 確信を持って配置できなかったキーワードを、理由とともに一覧にする（例: SERP の重なりが2件前後で意図も割れている、SERP 未確認、自サイトが作れないページの種類が優勢）。無理にどこかのクラスターへ入れない。

9. 最初の20ページの公開順を決める（新規とリライトを含む）。
   - 上位表示しやすいページ（03 のリストA）で、互いに自然にリンクし合えるページから始める。1つのピラーに属するクラスターを固めて出し、ピラーからのリンクとクラスター同士のリンクが早くそろうようにする。複数のピラーに少しずつ散らさない。
   - ピラーは、束ねるクラスターが数本そろう時点で公開する（中身のない入口を先に出さない）。
   - 03 のリストC の語を担当するページは、20ページに入れない。
   - 季節性のあるテーマ（03 のメモ列に山の月があるもの）は、山の前に公開・更新が済むように順番を前に出し、山の月を公開順の列に書く。
   - 優先度（手順7）と公開順が食い違うときは、公開順の列に理由を書く（例: 優先度は高いが、リンクを受けるクラスターがまだない）。

### まとめる・分けるの判断ルール

| 見るもの | まとめる（同じページで狙う） | 分ける（別ページ） |
|---|---|---|
| 上位10件の URL の重なり | 多い（目安: 3件以上） | 少ない（目安: 0〜1件） |
| 検索意図 | 同じ（例: どちらも比較検討） | 違う（例: 情報収集と取引） |
| SERP に出るページの種類 | 同じ（どちらも解説記事、どちらもカテゴリページ） | 違う（片方は記事、片方は商品一覧やツール） |

- 3つとも「まとめる」側ならまとめる。3つとも「分ける」側なら分ける。
- 重なりが2件前後で判断が割れるときは、意図とページの種類が一致していればまとめる。どちらかが違えば分ける。
- 閾値の「3件」は目安で、ジャンルに合わせて調整する。上位を大手サイトや Q&A サイトが占めるジャンルでは、閾値を上げる（4〜5件）。上位の顔ぶれが入れ替わりやすいニュース性の高い語では、日を変えて2回確認する。調整した閾値はマップの前提欄に書く。
- 1つの SERP に記事とカテゴリページが半々で出るなど、意図が割れている語は、自サイトが作れるページの種類に合うほうを主意図にする。もう一方の意図は別クラスターにするか、見送る。
- 表記ゆれのグループ（03）も同じルールで判断する。まとめた場合は、代表表記を担当ページの title・h1 に使い、別表記は本文で自然に使う。

### サイト種別ごとの注意

| サイト種別 | ページの役割分担 | 注意 |
|---|---|---|
| メディア | ピラー記事（テーマの総論と目次）とクラスター記事（個別の問い）。カテゴリページは記事一覧 | 同じ問いに答える記事が時期違いで複数ある状態が起きやすい。新規記事の前に既存記事の更新で済まないかを確認する。CV ページ（送客先、資料請求など）への導線をクラスターごとに決める |
| EC | カテゴリページ =「{商品カテゴリ}」「{商品カテゴリ} 通販」などの比較検討・取引意図。商品ページ = 商品名・型番（指名・取引）。記事 = 選び方・使い方（情報収集）で、カテゴリや商品へリンクする | SERP が商品一覧中心の語を記事で狙わない。絞り込み（色・サイズ・価格帯）の URL は、検索需要のある組み合わせだけインデックス対象にし、残りは robots.txt でクロールを止めるか URL フラグメント（`#`）で実装する。canonical・nofollow は効き目が弱い（[02-technical-audit.md](02-technical-audit.md) の「EC のファセット ナビゲーション」） |
| コーポレート（サービス業・BtoB） | サービスページ =「{サービス} 依頼」「{サービス} 料金」などの取引・比較検討意図。ブログ = 周辺の情報収集。事例ページ = 比較検討の後押し | ブログ記事とサービスページが同じ意図（例: 「{サービス} とは」をサービスページとブログの両方で狙う）にならないようにする。ブログからサービスページへのリンクを必ず置く |
| LP | 原則1意図1ページ | 広告用に作った訴求違い・地域違いの LP を大量にインデックスさせない。特定の地域や都市を対象に、内容がほぼ同じページを複数作って1つのページへ誘導する形は、Google のスパムポリシーの「誘導ページの不正使用」の例に当たる（鉄則6、[00-principles.md](00-principles.md)）。検索から流入させない LP は noindex にする |

### 判断の分岐（各クラスターの扱い）

| 判断 | 条件 | やること | やってはいけないこと |
|---|---|---|---|
| 新規 | 担当できる既存ページがなく、ほかのクラスターと意図が重ならない | 05 でブリーフを作る | 既存ページとの重複を確認せずに作る（鉄則7） |
| リライト | 担当ページはあるが、意図とずれている、情報が古い、論点が足りない | 05 でリライト用ブリーフを作り、06 で書き直す | URL を変える（必要がない限り） |
| 統合（301） | 同じ意図のページが2つ以上ある | 統合先を1つ決め、統合元の有用な内容を統合先に移してから、統合元を統合先へ 301 リダイレクトする。内部リンクは統合先へ直接張り替える | 内容を移さずにリダイレクトする。無関係なページ（トップページなど）へまとめてリダイレクトする |
| noindex | 読者には必要だが、検索からの流入を狙わない（サイト内検索の結果、会員向け、中身の薄いタグページなど。EC の絞り込みの組み合わせは上の「サイト種別ごとの注意」） | `<meta name="robots" content="noindex">` を設定する | 同じページを robots.txt でブロックする（クローラーが noindex を読めなくなる） |
| 削除（404 / 410） | 価値がなく、統合先に移すべき内容もなく、被リンク・流入・CV もない | 404 か 410 を返し、内部リンクを外す | 被リンクや流入があるページを確認せずに削除する |
| 維持 | 担当ページが意図に合っていて、問題がない | 変更しない。内部リンクだけ 08 で見直す | 「新しく見せる」ためだけに日付を変える |

統合先の選び方（上から順に比べる）:

1. 担当させたい検索意図に内容が合っているか。
2. CV（キーイベント）の実績が多いか。
3. 検索からのクリック数・表示回数が多いか。
4. 外部からの被リンクが多いか。
5. URL がクラスターの位置（階層）に合っているか。

1 が合わないページは、ほかの条件が良くても統合先にしない。統合先の内容を先に直し、統合元の URL をリダイレクトする。

### カニバリゼーションの確認手順

1. Search Console で1クエリずつ確認する。
   - 「検索パフォーマンス」→「検索結果」→「クエリ」タブで対象のクエリの行をクリックする（そのクエリでレポート全体が絞り込まれる）。表記ゆれをまとめて見るときは「+ フィルタを追加」→「クエリ」→「カスタム（正規表現）」を使う。
   - 「ページ」タブに切り替え、表示された URL と、それぞれのクリック数・表示回数・掲載順位を見る。
   - 期間は直近3か月を基本にし、変化を見るときは「比較」で前の期間と並べる。
2. サイト全体を一括で確認する。
   - Search Console API の `searchanalytics.query` で dimensions を `query` と `page`（入れ替わりを見るなら `date` も）にして取得する。1回の上限は25,000行で、`startRow` をずらして続きを取る。
   - Data Studio（旧 Looker Studio）の Search Console コネクタで「URL のインプレッション」表を選ぶと、クエリとランディングページを並べた表が作れる。
   - 大規模サイトは Search Console の一括データエクスポート（BigQuery）を使う。UI の表は1,000行までで、匿名化されたクエリは表に出ない。
3. 候補を抽出する。
   - 同じクエリで2つ以上の URL に表示回数がある行を抜き出す。
   - 2番目の URL の表示回数が1番目に比べて無視できない規模か（目安: 20%以上。閾値は調整可）を見る。
   - 日付を入れたデータで、表示される URL が週ごとに入れ替わっていないかを見る。入れ替わりがあるクエリは、同じ意図のページが競合している可能性が高いものとして優先して確認する。
4. 問題でないものを除く。
   - 意図が違うページが同じクエリにたまたま出ている（指名クエリでトップページと会社概要が出る、など）。
   - 2つの URL が同時に上位に並び、それぞれクリックを得ている。
5. 対処を決める。

| 状況 | 対処 |
|---|---|
| 同じ意図の2ページが入れ替わっている | 統合（301）。統合先の内容を先に強化し、内部リンクを統合先へ張り替える |
| 意図が違うのに、片方が誤ってそのクエリで出る | 各ページの title・h1・本文の焦点をそれぞれの意図に寄せる。誤って出るページから担当ページへ、意図どおりのアンカーテキストでリンクする |
| 片方は検索から流入させる必要がない | 片方を noindex にする |
| URL パラメータ違いなど、同じ内容の重複 URL | canonical で正規 URL を示す（[02-technical-audit.md](02-technical-audit.md)） |
| ピラーとクラスターが同じ意図を奪い合っている | ピラー側の該当部分を要約に縮め、クラスターへのリンクに置き換える |

- 内容の違うページを canonical で別のページに向けない。両方に noindex を付けない。片方を robots.txt でブロックしない。
- 対処を本番に反映した日を記録し、判定日（反映日 + 観察日数 + 遅延日数。[10-gsc-growth.md](10-gsc-growth.md) の「手順7 効果を測る」）に同じ手順で再確認する。判定日まで、同じページ・同じクエリ群に別の変更を入れない。

## 4. そのまま使えるプロンプト

```text
03 のキーワード一覧（{ファイル名}）と、各キーワードの上位10件の URL（{ファイル名 または 下に貼り付け}）から、トピカルマップを作ってください。
```

## 6. よくある失敗

- 1キーワードに1ページを割り当てる: 表記ゆれや言い換えのたびにページが増え、同じ意図のページが並ぶ。SERP の重なりでまとめる（鉄則7）。
- SERP を見ずに語の見た目でまとめる・分ける、重なりをドメイン単位で数える: 似た語でも意図が違うことがあり、大手サイトや Q&A サイトが並ぶジャンルではドメイン単位だと重なりを多く見積もる。上位10件を URL 単位で比べる。
- ピラーを増やしすぎる、ピラーにクラスターの本文まで書く: ピラーは最大6本にし、要約とクラスターへのリンクにとどめる。本文まで書くとピラーとクラスターが同じクエリを奪い合う。
- 配置に迷った語を無理にクラスターへ入れる: 意図の違う語が混ざり、ページの焦点がぼやける。理由を付けて「配置できなかったキーワード」に残す。
- 公開順を決めずに、書きやすいページから出す: リンクし合うページがそろわず、評価が積み上がらない。リストA の語で、同じピラーのクラスターから固めて出す。
- 内容を移さずに 301 する、無関係なページへまとめて 301 する: 統合元の有用な内容を統合先に移し、意図の合うページへリダイレクトする。
- noindex と robots.txt を併用する、内容の違うページを canonical で向ける: robots.txt でブロックすると noindex が読まれない。canonical は重複・ほぼ同じ内容の URL をまとめるためのもので、意図の違うページには使わない。
- EC でカテゴリページと記事が同じ取引意図を狙う: 取引・比較検討はカテゴリページ、選び方・使い方は記事、と役割を分ける。
- 地名だけ違う LP を量産する: 誘導ページとみなされるおそれがある。1意図1ページにし、広告専用の LP は noindex にする（鉄則6）。
- 構造を整えるためだけに既存 URL を変える: リダイレクトと内部リンクの張り替えの工数に見合う理由がなければ変えない。
