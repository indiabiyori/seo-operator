# 06 記事の執筆・リライト

05 のブリーフからの新規執筆と、既存記事のリライトの手順。一次情報の扱い、Google の品質ガイダンスに沿った編集チェック、AI が書いたように見える表現の除去、公開前の編集パスと人のパス、法的な表示の注意を扱う。

## 1. 目的

- 検索意図に答え、CV（問い合わせ・購入・資料請求など）への導線を持つ原稿を、サイトの文体ルールで書く（鉄則2）。
- 一次体験・独自データを創作せず、必要な箇所を `[要追加: ○○]` で見える形にする（鉄則5）。
- リライトでは、すでに順位が付いている論点・URL を失わずに改善し、変更の記録を残す。
- 初稿のまま公開しない。編集パスの採点と修正案、公開前に人が確認すべき事項（`[要追加]`、`[要確認]`、事実確認、禁止表現）を編集メモとして渡す。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|
| 文体・表記ルール | 作業フォルダの `seo/voice-guide.md` | 必須 | 執筆の依頼なので、先に初回セットアップ（[01-setup.md](01-setup.md)）を行う。ユーザーがセットアップより先に書くことを選んだ場合だけ、常体か敬体かを1問で確認し、編集メモに「voice-guide 未整備」と書く |
| サイト情報（CV、ターゲット、制約） | 作業フォルダの `seo/site-brief.md` | 必須 | 執筆の依頼なので、先に初回セットアップ（[01-setup.md](01-setup.md)）を行う。ユーザーが先に書くことを選んだ場合だけ、CV への導線を `[要追加: CVの定義]` として本文を進める。業種の法規制が不明なら、該当しうる箇所に `[要確認: 法務 ○○]` を付けるだけにする |
| コンテンツブリーフ（新規執筆） | [05-serp-brief.md](05-serp-brief.md) の出力 | 新規は必須 | 05 を先に実行する。急ぐ場合は対象キーワード・検索意図・想定読者・CV の4点を聞いて簡易ブリーフを作り、ユーザーの確認を取ってから書く |
| 既存記事の本文と公開URL（リライト） | CMS の編集画面から本文をコピー、または公開ページの URL | リライトは必須 | 本文を貼ってもらう。URL だけならページ取得ツールで取得し、取れなかった部分（JavaScript で描画される部分など）を編集メモに書く |
| 対象ページのクエリ別データ（リライト） | Search Console →「検索パフォーマンス」→「検索結果」→ ページのフィルタで対象 URL を指定 →「クエリ」タブ →「エクスポート」 | リライトは必須 | 順位の付いている論点を特定できないため、既存の見出し・論点は削除も統合もしない前提で進め、エクスポートを依頼する |
| 一次情報（体験、独自データ、事例、写真、専門家の確認） | ユーザー・社内の担当者・監修者 | 任意（あるほど質が上がる） | 創作しない。`[要追加: ○○]` を残し、誰に何を聞けば埋まるかを編集メモに書く（鉄則5） |
| 事実の出典（統計・法令・料金・仕様） | 公的機関・メーカー・一次資料の URL | 数値や断定を書くなら必須 | 出典のない数値は書かない。`[要追加: ○○の出典]` を残す（鉄則1） |

## 3. 手順

### 共通の準備

1. `seo/voice-guide.md` と `seo/site-brief.md` を読む。ないときは「2. 必要な入力データ」の動き方に従う。`最終更新日` が6か月以上前なら見直しを提案する（SKILL.md の初回セットアップと同じ基準）。
2. 新規かリライトかを決める。対象キーワードと同じ検索意図の既存ページがあれば、新規ではなくリライトか統合にする（鉄則7、[04-topical-map.md](04-topical-map.md)）。既存ページの有無が不明なら、Search Console のページ別データか `site:example.jp {キーワード}` の検索結果で確かめてから書く。
3. 記事が担う CV を1つ決め、導線を置く位置を先に決める（鉄則2）。導線は本文の流れで必要になった箇所に置き、冒頭と末尾に同じ宣伝文を繰り返さない。

### 新規執筆（05 のブリーフから）

1. ブリーフの見出し構成を使う。変える場合は理由を編集メモに書く（ブリーフは SERP 分析に基づくため、無断で崩さない）。
2. 冒頭で検索者の質問に直接答える。2〜3文、100〜150字程度の、単独で引用できる完結した文にする（鉄則4）。読者の悩みを並べる前置きや一般論の前置きは書かない。
3. 各節は、見出しへの答えを最初の1〜2文で書き、そのあとに理由・条件・例を書く。どの節にも具体的なもの（出典付きの数値、固有名のツールや制度、例、手順）を1つ以上入れ、一般論だけの節を作らない。定義は1文、手順は番号付きリスト、比較は表にする。
4. 段落は3文以内を目安にする。同じ論点を2つの節で繰り返さない。両方の節で必要なら、一方で説明し、もう一方からはその節を参照する。
5. 主キーワードは、最初の段落、H2 のどれか1つ、結びに自然に入れる。副キーワードは合う箇所だけに入れ、無理に詰めない。
6. 一次情報が必要な箇所に `[要追加: ○○]` を置く（下の「一次情報と [要追加] の書き方」）。体験談・社内データ・事例・専門家コメントは、提供されたものだけを使う。
7. 数値・固有名詞・法令・料金・仕様には出典を付ける。出典がなければ書かないか `[要追加: ○○の出典]` にする。料金・法改正・ツールの画面など時期で変わる情報には確認日を併記する。
8. 結びは本文の要約にしない。読者の次の行動（CV への導線、次に読むページ、準備するもの）で終える。
9. 品質チェック、法的表示のチェック、禁止表現チェック（英語ページは英語のリスト）を順に行い、下の「編集パスと人のパス」に回す。

### リライト（既存記事の改善）

1. クエリ別データを読み、表示回数のあるクエリを原稿の見出し・段落に対応づける。対応する論点がないクエリは「追記候補」、論点はあるのに順位が低いクエリは「改善候補」に分ける。
2. 次の判断ルールで変更範囲を決める。
   - 順位が付いているクエリ（表示回数があるもの）に対応する論点・見出しは消さない。統合するときは、その論点を別の節に移して残す。
   - URL を変えない。どうしても変えるなら旧 URL から新 URL へ 301 リダイレクトを設定し、内部リンク・canonical・サイトマップを新 URL にそろえる（[08-internal-linking.md](08-internal-linking.md)、[02-technical-audit.md](02-technical-audit.md)）。
   - 実質的な変更がないのに更新日だけを変える「見せかけの鮮度」をしない。Google は、内容を実質的に変えずに新しく見せるために日付を変えることを、検索エンジン向けコンテンツの兆候として挙げている。誤字修正や言い回しの調整だけなら更新日は変えない。
   - title・meta description は [07-on-page.md](07-on-page.md) の手順で直す。本文と同じ日に変えるなら、変更履歴に両方を書く。
   - 一度に変える範囲は、後から「何が効いたか」を追える単位にする。
3. 誤りは訂正し、訂正したことを本文の注記か変更履歴に残す。情報を削るときは、その情報を目的に来ているクエリがないかを先に確認する。
4. 変更履歴を残す（「5. 出力フォーマット」の変更履歴の表）。各変更に分類を1つ付ける: `meta-rewrite`（title・meta description）/ `content-gap`（不足した論点の追加）/ `internal-link`（内部リンク）/ `real-data`（一次データ・事例）/ `structure`（見出し構成・ページ構造）。反映したら、[10-gsc-growth.md](10-gsc-growth.md) の変更ログにも1行（反映日・URL・対象クエリ・分類・変更前の値・判定予定日）を書く。08 と 10 は、この変更ログで判定待ちのページを確かめる。
5. 効果は、本番への反映日を起点に実測で判定する（[10-gsc-growth.md](10-gsc-growth.md) の「手順7 効果を測る」）。
   - 判定日 = 反映日 + 観察日数 + データの遅延日数。観察日数は28日が基本で、遅延3日なら反映日の31日後に判定し、窓は反映日の翌日から28日間（D+1〜D+28）。7日で見るのは、表示回数が十分に多いページで変化の兆しを早く見る場合だけ。
   - 比較対象は、反映前の同じ長さ・同じ曜日構成の期間。同じカテゴリで変更していないページ（対照）の、同じ2つの期間の増減も並べる。判定日までは、同じページ・同じクエリ群に別の変更を入れない。
   - 判定は改善・変化なし・悪化・判定不能の4つ。報告するのは「何を変えたか」と判定予定日まで。効果を予測で断定しない。「変化なし」「悪化」と判定できたら、次の打ち手は別の分類から選ぶ。「判定不能」なら、分類を変えずに観察を延ばす。

### 一次情報と [要追加] の書き方

- 形式は `[要追加: 何を / 誰から・どこから / どの形式で]`。例: `[要追加: 導入企業の事例1件。業種・導入前の課題・導入後の変化。先方の掲載許可があるもの]`。
- 該当する段落の直後に置く。前後の文は、要追加が埋まらなくても意味が通るように書く。
- 書いてはいけないもの:
  - 創作した体験談（「実際に使ってみたところ」「編集部で検証した結果」など、実施していない検証）
  - 架空の専門家・利用者のコメント、実在する人物の発言を装った作文
  - 出典のない数値（「約8割の人が」「平均○円」など）、架空のアンケート結果、独自調査を装った推計
- 受け取った体験・データは原文のまま使い、要約や編集をした場合は編集メモにその内容を書く。

### 品質チェック（Google の「有用で信頼性の高い、ユーザー第一のコンテンツ」から）

Google 検索セントラルの自己評価の質問と E-E-A-T の説明を、執筆・編集のチェック項目にしたもの（ガイダンスの確認日: 2026-09-25）。

| 観点 | チェック項目 | 満たさないときの対応 |
|---|---|---|
| Who（誰が） | 著者が明確か。著者情報が求められる内容では署名（バイライン）があり、著者の経歴・専門分野のページにつながっているか | `[要追加: 著者名と経歴]` を残す。監修者を架空で置かない |
| How（どのように） | 調査・検証・テストの方法を説明しているか。AI や自動化の使用を読み手が気にする内容なら、使い方を開示しているか | 方法の説明を足す。検証していないことを検証したように書かない |
| Why（なぜ） | 検索流入のためではなく、読者の役に立つために書いているか | 読者の課題に答えない節を削る |
| 独自性 | 独自の情報・分析・データを含むか。他の情報源をまとめただけになっていないか | `[要追加: 独自データ・事例]` を置き、ないまま公開するかをユーザーに判断してもらう |
| 見出し・タイトル | 内容を要約しているか。誇張やショックを与える表現になっていないか | [07-on-page.md](07-on-page.md) の手順で直す |
| 完結性 | 読み終えた人が、同じことをもう一度検索し直さずに済むか | 足りない論点を追記候補に入れる |
| 分量 | 特定の文字数を目標にしていないか（Google は優先する文字数は存在しないと明記している） | 論点の過不足で分量を決める |
| 経験 | 実際の経験がないのに、経験があるように書いていないか | 経験の部分を `[要追加]` に置き換える |
| 日付 | 実質的な変更なしに日付を更新していないか | リライトの判断ルールに従う |
| 信頼性（E-E-A-T） | 出典・著者・運営者情報で内容の正確さを確かめられるか。Google は E-E-A-T のうち信頼性を最も重いものとし、健康・お金・安全など YMYL の話題では特に重く見る | 出典を付ける。確かめられない記述は削る |
| 生成 AI の利用 | 生成 AI の利用自体は問題にならない。価値を加えないページを大量に作ると、大量生成されたコンテンツの不正使用に当たるおそれがある（[00-principles.md](00-principles.md)） | 1記事ずつ編集パスと人のパスを通し、独自の情報を加える |

- E-E-A-T 自体は直接のランキング要因ではない（Google の説明）。チェックの観点として使い、点数化しない。

### 法的な表示の注意（判断はしない）

法的な判断はしない。該当しうる箇所の直後に `[要確認: 法務 {論点}（確認先: {法務担当・監修者}）]` を置き、編集メモの「法的注意の箇所」に載せる。確認するのはユーザー側の法務担当や専門家。HTML コメントの注記は公開プレビューに表示されず、確認漏れのまま公開されるので使わない。

| 論点 | 該当しうる表現・箇所 | `[要確認: 法務 ○○]` に書くこと |
|---|---|---|
| ステルスマーケティング規制（景品表示法、2023年10月1日施行） | 事業者から依頼や対価を受けた紹介、アフィリエイトリンク、自社商品を第三者の感想のように見せる記述、好意的な顧客の声だけを選んだ抜粋 | 広告であることが明瞭か（「広告」「PR」などの表示、文字の大きさ・位置）。消費者庁のステマ告示の運用基準と Q&A で確認する |
| No.1表示・最上級表現 | 「No.1」「顧客満足度1位」「業界最安」「最高品質」 | 合理的な根拠（調査の対象者・比較対象・時期）を示せるか。消費者庁「No.1 表示に関する実態調査報告書」（2024年9月）を参照する |
| 優良誤認・有利誤認（景品表示法） | 効果・性能の断定、「今だけ」「通常価格○円のところ」などの価格表示 | 根拠資料と価格の実態を確認する |
| 打消し表示 | 強調した表示を「※個人の感想です」などの注記で打ち消す書き方 | 強調表示と注記の関係が読み手にわかる形か |
| 薬機法など（医薬品・化粧品・健康食品・医療機器の広告） | 病気の治療・予防をうたう表現、承認や届出の範囲を超える効能効果。医薬品でない健康食品に医薬品のような効能を書く表現 | 承認・届出の範囲を超えていないか。薬機法第66条は「何人も」を対象にするので、広告主だけでなく記事の書き手・メディアも対象になる |
| その他の業種規制 | 医療機関、金融商品、不動産、士業など | site-brief の制約欄を見て、業種の広告ルールに照らして確認する |
| レビュー・口コミ | 実体験に基づかないレビュー、特典と引き換えに書かれ開示のないレビュー | Google のレビュー スニペットのガイドラインも、偽のレビューや開示のないインセンティブ付きレビューを載せないよう求めている |
| 引用・転載 | 他サイトの文章・画像・図表 | 出典の明記と、引用部分が本文に対して従になっているか |

### AI が書いたように見える禁止表現リスト（日本語）

どれも単体では誤りではない。頻度と、情報を運んでいるかで判断する。

| # | 表現・パターン | なぜ不自然か | 言い換えの方針 |
|---|---|---|---|
| 1 | 「いかがでしたか」「いかがでしたでしょうか」 | 締めの定型で情報がない | 削除する。最後は次の行動（CV への導線、関連記事）か、残る注意点で終える |
| 2 | 「〜と言えるでしょう」「〜と言えます」 | 根拠を示さずに結論らしく見せる | 根拠があれば理由を添えて言い切る。なければ条件を書く |
| 3 | 「結論から言うと」の多用 | 繰り返すと定型に見える。結論を先に書けば前置きは要らない | 前置きを消し、結論の文から始める |
| 4 | 「〜していきましょう」「〜見ていきましょう」の連発 | 呼びかけだけが続き、行動の中身がない | 何をするかを手順で書く。見出しで予告済みなら削る |
| 5 | 過剰な「重要です」「大切です」「欠かせません」 | 強調が均等に置かれ、どこが要点かわからなくなる | やらないと何が起きるかを書き、「重要」の語は消す |
| 6 | 最後にまとめを繰り返すだけの段落 | 本文の言い直しで新しい情報がない | 削除するか、判断の早見表・次の行動に置き換える |
| 7 | 毎節の同型の導入（「ここでは〜について解説します」） | 節ごとに同じ予告が入り、テンプレートに見える | 見出しへの答えから書き始める |
| 8 | 三点セットの箇条書きの連続 | 論点の数に関係なく3項目にそろえる癖 | 論点の数だけ書く。つながりのある内容は文章で書く |
| 9 | 見出しの「〜とは？」の乱発 | 定義が要らない節まで同じ形になり、目次が単調 | 定義の節だけに使う。ほかの見出しは節の結論か問いの中身を書く |
| 10 | 太字の乱用 | 1段落に何か所もあると要点が埋もれる | 読み飛ばされると困る語だけにする（1節に1か所程度） |
| 11 | 根拠のない「さまざまな」「多くの」「多数の」 | 具体を省いた印象で、情報量がない | 具体例を挙げるか、数を出典付きで書く。挙げられなければ削る |
| 12 | 「近年、〜が注目されています」「〜の重要性が高まっています」 | 誰でも書ける一般論の前置き | 削除する。変化があるなら、何が・いつ・どう変わったかを出典付きで書く |
| 13 | 「〜ではないでしょうか」 | 断定を避ける逃げ道。多用すると主張が消える | 言い切るか、言い切れない条件を書く |
| 14 | 「〜と言われています」「〜という声もあります」 | 誰が言ったかわからない権威づけ | 発言者・出典を書く。なければ削る |
| 15 | 「一概には言えません」「ケースバイケースです」 | 判断を読者に丸投げする保険 | 何によって変わるかと、条件ごとの答えを書く |
| 16 | 「効果的な」「最適な」「包括的な」「多角的な」 | 中身を説明しない形容 | 何に対してどう効くか、どの観点から見たかを書く |
| 17 | 「不可欠」「鍵となる」「カギを握る」 | 強調の感触だけを足す | なくすと何が起きるかを書く |
| 18 | 「〜することができます」「〜することが可能です」 | 「〜できる」で足りる冗長な形 | 「〜できる」か動詞の言い切りにする |
| 19 | 「ぜひ〜してみてください」の締め | 毎回同じ締めになる | どのページで何をすればよいかを書く |
| 20 | 「〜が挙げられます」の連続 | 列挙の定型が続き、各項目の説明が薄い | 表か箇条書きにして、各項目に理由を付ける |
| 21 | 「理由は3つあります」などの数の宣言 | 数に合わせて弱い項目が混じる | 数を宣言せず、理由の中身から書く |
| 22 | 「実は」「驚くべきことに」の乱用 | 意外でない情報に演出だけを付ける | 削除する。意外さは事実の対比で示す |
| 23 | 「〜ではなく、〜」の対比の繰り返し | 同じ構文が続くとリズムが目立つ | 1記事に数回までにし、残りは素直な肯定文にする |
| 24 | 段落頭の「さて」「それでは」「このように」 | 内容を運ばない橋渡し語 | 前の段落の内容でつなぐか、削る |
| 25 | 「〜と言っても過言ではありません」「〜に他なりません」 | 決め台詞の演出 | 事実だけを書く |
| 26 | タイトル・見出しの「徹底解説」「完全ガイド」「〇選」の乱用 | 中身と釣り合わない誇張に見える | 記事が扱う範囲を書く（[07-on-page.md](07-on-page.md) の手順で文字数も確認） |
| 27 | 冒頭で悩みを並べる定型（「〜で悩んでいませんか？」「そんなあなたに」） | どの記事にも使える導入で、答えが遅れる | 検索意図への答えから始める |
| 28 | 冒頭の「本記事では〜を解説します」と直後の目次の重複 | 同じ情報を2回示している | どちらかにする。予告するなら、記事で得られる結論を1文で書く |
| 29 | 同じ文末の連続（「〜です。〜です。〜です。」） | リズムが単調になる | 文の長さと文末を変える |
| 30 | 地の文での体言止めの多用 | 説明が途切れ、メモ書きのようになる | 述語まで書く |
| 31 | 全段落が同じ長さ・同じ文数 | テンプレートで作った印象を与える | 論点の重さに合わせて段落の長さを変える |
| 32 | メリットとデメリットを必ず同数で並べる | 実態と関係なく対称にそろえている | 実際にある分だけ書く |
| 33 | 根拠のない推奨（「〜がおすすめです」「〜しておくと安心です」） | 誰に・なぜ勧めるかがない | 条件（どんな人・状況なら）と理由を書く |
| 34 | 「注意が必要です」の連発 | 何にどう注意するかがない | 起きうる問題と避け方を書く |
| 35 | 記事末尾に毎回付く定型の「よくある質問」 | 本文の繰り返しになりやすい。Google の FAQ リッチリザルトは2026年5月7日以降、Google 検索に表示されない（[07-on-page.md](07-on-page.md)） | 読者が実際に持つ質問（問い合わせ・検索クエリ）があるときだけ置く |
| 36 | 「〜において」「〜を活用することで〜を実現」などの翻訳調 | 英語の構文をなぞった硬い言い回し | 「〜で」「〜を使うと〜できる」に直す |

### 禁止表現の直し方

- 同義語への置き換えで済ませない。「重要です」を「大切です」に替えても、文が何も運ばないことは変わらない。
- 手順: （1）その文が伝えている情報を1つ書き出す。（2）情報がなければ文ごと削除する。（3）情報があれば、条件・数値（出典付き）・固有名・手順で書き直す。（4）具体化の材料がなければ `[要追加: ○○]` を置く。
- 例（架空の EC 向け記事）:
  - 前:「在庫管理は非常に重要です。さまざまなツールがあるので、自社に最適なものを選びましょう。」
  - 後:「在庫数と受注数がずれると、欠品による受注取り消しが起きる。ツールを比べる前に、扱う商品数と、在庫を連携したい販売チャネル（自社 EC、モールなど）を書き出す。[要追加: 自社で起きた欠品の事例]」
- 同じ表現が1記事に2回以上出たものから優先して直す。1回だけでも、情報を運んでいなければ直す。

### 編集パスと人のパス（初稿のまま公開しない）

AI の初稿は、次の2つのパスを終えるまで公開しない。価値を加えないまま公開を重ねると、大量生成されたコンテンツの不正使用に当たるおそれがある（[00-principles.md](00-principles.md)）。

1. 編集パス（Claude）: 厳しい編集者の立場で、ブリーフと `seo/voice-guide.md` に照らして次の4観点を1〜10で採点し、理由を1行ずつ書く。ブリーフ（上位5件の分析）がなければ (1)(2) は「未評価」とする。
   - (1) 現在の上位ページより早く、質問に答えているか
   - (2) 上位5件にない情報（一次情報、独自の分析、手順の細部）があるか
   - (3) 生成されたように聞こえる文がないか（禁止表現リスト）
   - (4) 事実が不確かな箇所。出典が必要な主張をすべて挙げ、出典の候補を示す
2. 影響の大きい修正を10個、影響の大きい順に出す。対象の文をそのまま引用し、置き換え案を並べる。置き換え案にも体験や数値を作らず、材料がなければ `[要追加: ○○]` にする。
3. 人のパス（ユーザー）: 声に出して読み、引っかかる文を直す。`[要追加]` と `[要確認]` を埋める。編集パスで挙がった事実をすべて一次資料で確認する。自分の経験・データ・意見を足す（同じモデルを使う競合には書けない部分）。

## 6. よくある失敗

- AI の下書きを編集せずに公開する: 定型の言い回しが残り、上位ページにない情報も入らない。編集パスと人のパスを終えるまで公開しない。人が足す経験・データ・意見を省かない。
- 体験談や事例を「それらしく」補う: 事実でないと分かれば信頼を失う。`[要追加]` のまま渡し、埋まらなければその節を外すかどうかをユーザーに決めてもらう。
- 禁止表現を同義語に置き換えて終える: 文の中身は増えない。情報のない文は削り、情報のある文は具体化する。
- リライトで順位の付いている見出しを削る: クエリ別データと見出しを対応づけてから構成を変える。データがなければ削除・統合をしない。
- 更新日だけを新しくする: 実質的な変更があるときだけ更新日を変え、変更履歴に理由を書く。
- URL を整理のために変える: 変えない。変えるなら 301、内部リンク、canonical、サイトマップを同時に直す。
- 文字数を目標にする: Google は優先する文字数はないとしている。論点の過不足で分量を決める。
- 法的な判断を書いてしまう: 「問題ありません」と書かない。該当しうる箇所に `[要確認: 法務 ○○]` を置き、確認先を示すまでにとどめる。HTML コメントの注記にしない。
- 生成 AI で似た記事を量産する: 大量生成されたコンテンツの不正使用に当たりうる（鉄則6、[00-principles.md](00-principles.md)）。1記事ごとに独自の情報を加えられる本数に絞る。
- 判定の前に同じページへ別の変更を入れる: どの変更が効いたか分からなくなる。変更履歴に反映日・分類・判定予定日を書き、判定日まで同じページ・同じクエリ群を触らない（[10-gsc-growth.md](10-gsc-growth.md)）。
